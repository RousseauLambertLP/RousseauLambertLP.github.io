## 1. GDAL fusionne le correctif pour la course de threads Windows

**Fusion : 3 novembre 2026 à 09:16 HNE · Statut : correctif fusionné dans `master`, pas encore publié dans une version · Importance pratique : moyenne et conditionnelle pour les traitements raster sous Windows.**

Le problème signalé le 30 octobre n’est plus seulement accompagné d’une proposition : le correctif a maintenant été intégré à GDAL. Sur Windows, un thread créé par `CPLCreateJoinableThread()` pouvait terminer avant que son handle soit enregistré. Le code pouvait alors le traiter comme un thread détaché et libérer sa structure interne, avant qu’une deuxième libération ait lieu lors de `CPLJoinThread()`.

Le changement ajoute un indicateur explicite `bJoinable`, défini avant la création du thread, afin que seul un thread réellement détaché libère lui-même cette structure. Le cas documenté combinait plusieurs processus Python avec `gdal.Warp(..., multithread=True)`. Le chemin pthread utilisé sous Linux n’est pas concerné selon l’analyse du correctif.

**Pourquoi ça te concerne :** des chaînes raster peuvent superposer du parallélisme au niveau des processus et le multithreading interne de GDAL. Sur des postes ou traitements batch Windows, cette combinaison pouvait provoquer un arrêt du processus plutôt qu’une erreur GDAL récupérable. Les services Linux ne justifient pas de changement général sur la base de ce correctif.

**Action : à tester et à suivre.** Conserver un test de stress Windows couvrant plusieurs processus et `gdal.Warp(multithread=True)`. Si ce scénario est utilisé, attendre une release GDAL contenant le commit avant de considérer le problème corrigé dans les environnements distribués; le code fusionné seul ne modifie pas les installations existantes.
