## 1. Serveurs MCP 2.2.0 : certificats compromis retirés et nouveaux correctifs de sécurité

**Publication : 28 octobre 2026 · Statut : version 2.2.0 publiée · Importance pratique : élevée pour les déploiements des serveurs MCP officiels.**

La version **2.2.0** de `modelcontextprotocol/servers` actualise le bundle `certifi` du conteneur de `mcp-server-fetch` après la divulgation d’eMudhra concernant des clés privées récupérables pour huit certificats intermédiaires. `certifi 2026.10.23` retire les racines `emSign Root CA - C1` et `emSign ECC Root CA - C3`. Les installations PyPI récentes résolvent la version actuelle de `certifi`, mais un environnement créé avant le 23 octobre peut conserver l’ancien bundle.

La version publie aussi `mcp-server-fetch 2026.10.28`, avec notamment un refus des destinations IPv6 compatibles IPv4, une politique plus prudente lorsque `robots.txt` répond en erreur 5xx et plusieurs correctifs d’extraction HTML. Pour les serveurs TypeScript, la validation TLS dépend du runtime Node.js; les notes recommandent Node.js **24.22.1**, **26.12.1** ou une version ultérieure.

**Pourquoi c’est pertinent :** un serveur Fetch qui consulte de la documentation, des catalogues ou des API météo se trouve sur une frontière réseau sensible. La confiance TLS et les protections SSRF font partie du modèle de sécurité de l’agent, indépendamment de la qualité du modèle de langage.

**Action : à mettre à jour.** Vérifier la version du dépôt ou des paquets, rafraîchir les environnements `mcp-server-fetch` existants avec `uvx --refresh` ou mettre `certifi` à jour, et vérifier la version réelle de Node.js utilisée par les serveurs TypeScript. Une simple contrainte `engines: node 24` ne garantit pas un runtime corrigé.

**Source primaire :** [modelcontextprotocol/servers — version 2.2.0](https://github.com/modelcontextprotocol/servers/releases/tag/v2.2.0).

## 2. MCP : la sélection forcée d’outils peut contourner l’intention des annotations

**Ouverture : 1er novembre 2026 · Statut : demande de clarification ouverte, pas une vulnérabilité confirmée ni un changement de spécification · Importance pratique : élevée pour la conception d’agents avec outils d’écriture.**

Une issue de la spécification MCP souligne que `readOnlyHint` et `destructiveHint` sont explicitement non fiables lorsqu’ils proviennent d’un serveur non approuvé, mais que la spécification n’explique pas complètement comment un client doit composer un sous-ensemble d’outils lorsque l’API du modèle force un appel. L’auteur rapporte **460 appels d’écriture sur 816 essais** avec des outils simulés lorsqu’un appel était forcé, contre **5 sur 816** sans cette contrainte; limiter l’ensemble aux classes d’outils autorisées aurait produit 0 écriture dans ces essais.

Ces résultats sont ceux de l’auteur, sur quatre modèles hébergés, et n’ont pas été validés indépendamment par les responsables MCP. La discussion reconnaît toutefois le problème conceptuel : rien reçu d’un serveur non approuvé ne devrait élargir l’ensemble des outils qu’un client est prêt à forcer.

**Pourquoi c’est pertinent :** un agent qui expose des outils de lecture et de modification pour des API ou des données peut choisir une opération d’écriture simplement parce que l’outil de lecture attendu n’est pas disponible dans le sous-ensemble présenté. Les annotations sont des indications, pas un mécanisme d’autorisation.

**Action : à tester et à durcir.** Séparer les outils de lecture et d’écriture par politique locale, construire la liste d’outils autorisés avant toute sélection forcée, et refuser ou revenir à une génération sans outil lorsque cette liste est vide. Ne pas faire dépendre une autorisation d’écriture d’annotations fournies par un serveur non approuvé.

**Sources primaires :** [issue MCP #3492](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/3492) · [spécification MCP — Tool annotations](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#tool).

## 3. xarray : ouverture automatique des répertoires Zarr corrigée sous Windows

**Fusion : 31 octobre 2026 · Statut : correctif fusionné dans `main`, pas encore publié dans une version xarray · Importance pratique : moyenne pour les traitements Zarr sous Windows.**

xarray essayait de lire un « magic number » pendant la détection du moteur. Sous Windows, ouvrir un répertoire Zarr de cette manière peut produire `PermissionError` plutôt que `IsADirectoryError`, interrompant `open_dataset()` avant que le backend Zarr inspecte le store. Le correctif fusionné teste d’abord si le chemin est un répertoire; il couvre les formats Zarr 2 et 3, avec des chemins `str` et `Path`.

**Pourquoi c’est pertinent :** les notebooks, postes de développement et chaînes locales Windows peuvent échouer à ouvrir un store Zarr valide alors que les mêmes données fonctionnent ailleurs. Ce correctif réduit une différence de comportement entre plateformes, mais il n’est pas encore disponible dans une version publiée.

**Action : à suivre.** Conserver un test d’ouverture automatique d’un répertoire Zarr local dans la matrice Windows et attendre la prochaine version xarray contenant le commit. Utiliser explicitement `engine="zarr"` peut être évalué comme contournement local, sans être présenté comme le correctif amont.

**Source primaire :** [pydata/xarray — pull request #11802](https://github.com/pydata/xarray/pull/11802).

## 4. OKF : proposition pour empêcher un agent de confirmer sa propre production

**Ouverture : 31 octobre 2026 · Statut : proposition ouverte dans le dépôt canonique, non intégrée à OKF v0.2 · Importance pratique : à surveiller pour les connaissances maintenues par des agents.**

OKF v0.2 classe actuellement un concept comme `machine-confirmed` lorsqu’il contient un événement `verified` provenant d’un acteur non humain. Une nouvelle proposition observe que l’agent indiqué dans `generated.by` peut aussi s’inscrire lui-même dans `verified`, atteignant ainsi ce niveau sans contrôle indépendant. Elle propose que les consommateurs ignorent, pour le calcul du niveau de confiance, une vérification provenant du même producteur non humain.

Il s’agit d’une proposition communautaire : la spécification **n’a pas changé** et aucune nouvelle version n’a été publiée.

**Pourquoi c’est pertinent :** une base de règles ou de connaissances météo exploitable par des agents doit distinguer génération, validation déterministe et revue indépendante. Une étiquette de confiance perd de sa valeur si le même agent peut à la fois produire et confirmer le contenu.

**Action : à appliquer comme règle de prototype, pas comme exigence OKF.** Utiliser des identités de producteurs distinctes pour la génération et la vérification, conserver les résultats des contrôles déterministes et ne pas présenter cette règle comme normative tant qu’elle n’est pas fusionnée et versionnée.

**Sources primaires :** [proposition OKF #60](https://github.com/GoogleCloudPlatform/open-knowledge-format/issues/60) · [spécification canonique OKF v0.2](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md).
