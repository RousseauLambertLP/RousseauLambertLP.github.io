Six changements récents dépassent le seuil de publication. Le standard OGC du 12 novembre est inclus comme rattrapage daté; les cinq correctifs de code ont été fusionnés après l’édition précédente. Aucun de ces correctifs n’est encore inclus dans une release publiée.

## 1. OGC API — Common Part 2: Geospatial Data devient un standard 1.0

**Date :** 12 novembre 2026  
**Statut :** standard OGC 1.0 publié; approbation datée du 15 octobre 2026  
**Importance pratique :** élevée pour l’architecture des OGC API et la réutilisation des collections

OGC API — Common Part 2 formalise les éléments communs permettant à une API Web de lister et de décrire ses collections de données géospatiales. Il fournit une base partagée que les standards OGC API spécialisés peuvent réutiliser au lieu de redéfinir séparément la découverte et la description des collections.

**Pourquoi ça concerne les praticiens :** une implémentation GeoMet ou pygeoapi qui expose plusieurs familles de données gagne à aligner ses métadonnées de collections et ses déclarations de conformité sur cette base commune. Cela réduit les écarts entre OGC API — Features, Coverages, EDR et d’autres API, et facilite la création de clients génériques ou d’outils d’agents capables de découvrir les ressources de façon déterministe.

**Action possible :** à évaluer. Comparer les réponses `collections` et les déclarations de conformité existantes avec les exigences de Part 2 avant toute évolution d’API; traiter le document comme un standard adopté, et non comme une proposition.

**Source primaire :**

- Standard OGC API — Common — Part 2: Geospatial Data 1.0 : <https://docs.ogc.org/is/20-024/20-024.html>

## 2. GDAL corrige le resampling ignoré lors d’une lecture redimensionnée de Warped VRT

**Date :** 16 novembre 2026  
**Statut :** correctif fusionné dans `master`; absent de la release GDAL 3.13.3 actuellement publiée  
**Importance pratique :** élevée pour les chaînes de reprojection et de redimensionnement raster

Le chemin optimisé de `VRTWarpedDataset::IRasterIO()` utilisait le resampling du warp et pouvait ignorer l’algorithme demandé lors d’une lecture complète vers un tampon de taille différente. Une chaîne `reproject` suivie de `resize -r average` pouvait donc produire un résultat nearest-neighbour. Le correctif réserve maintenant ce raccourci au nearest-neighbour.

**Pourquoi ça concerne les praticiens :** le choix du resampling change directement les valeurs de grilles météorologiques, d’accumulations et d’indices continus. Dans le cas de test du projet, des bandes 0/200 restent à 0/200 avant le correctif, alors que l’agrégation attendue produit environ 88 à 111.

**Action possible :** à tester et à suivre. Ajouter un test numérique qui compare une chaîne reprojection+resize à deux opérations séparées pour `average`, `bilinear` ou l’algorithme réellement utilisé; attendre une release GDAL contenant le correctif avant la production.

**Sources primaires :**

- Pull request GDAL #15427 : <https://github.com/OSGeo/gdal/pull/15427>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/aeb88659f230e86bde92fa6519dcb92bb0e4ba08>
- Releases GDAL : <https://github.com/OSGeo/gdal/releases>

## 3. GDAL évite un décalage de pixel dans certaines lectures GeoTIFF multithread

**Date :** 16 novembre 2026  
**Statut :** correctif fusionné dans `master`; absent de la release GDAL 3.13.3 actuellement publiée  
**Importance pratique :** élevée pour les mosaïques et lectures par fenêtres fractionnaires

Avec une fenêtre exprimée en coordonnées pixel flottantes et `GDAL_NUM_THREADS` supérieur à 1, le chemin GeoTIFF multithread pouvait ignorer la fenêtre fractionnaire et utiliser les coordonnées entières tronquées. Le signalement reproduit une différence d’une colonne — 800 avec un thread contre 799 avec deux — et décrit des morceaux de mosaïque Copernicus décalés d’un pixel sans erreur. GDAL désactive maintenant ce chemin multithread pour ces fenêtres et émet un avertissement.

**Pourquoi ça concerne les praticiens :** les conversions de bbox vers fenêtres pixel produisent souvent de petites erreurs flottantes, surtout pour des résolutions géographiques comme 1/3600°. Un traitement parallèle pouvait donc être rapide mais spatialement incohérent avec le même traitement monothread.

**Action possible :** à tester. Rejouer les lectures de fenêtres issues de bbox avec un et plusieurs threads et comparer les pixels de bord; surveiller l’avertissement ajouté par GDAL et attendre une release contenant le correctif.

**Sources primaires :**

- Signalement GDAL #15513 : <https://github.com/OSGeo/gdal/issues/15513>
- Pull request GDAL #15529 : <https://github.com/OSGeo/gdal/pull/15529>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/f6983b320bf6fc3758f71d49bbd4fe968c5ff7cc>

## 4. Zarr corrige l’ordre de décodage de filtres Numcodecs après une transposition

**Date :** 16 novembre 2026  
**Statut :** correctif fusionné dans `main`; absent de la release Zarr-Python 3.4.2 actuellement publiée  
**Importance pratique :** élevée pour l’intégrité des tableaux utilisant des filtres et `TransposeCodec`

Des tableaux combinant un filtre Numcodecs `Delta` ou `FixedScaleOffset` avec `TransposeCodec` pouvaient être décodés dans l’ordre mémoire plutôt que dans l’ordre logique, puis relus avec des valeurs mélangées. Le correctif rend le tampon contigu en ordre C avant le décodage et étend les tests de round-trip avec transposition.

**Pourquoi ça concerne les praticiens :** il s’agit d’un problème de fidélité des valeurs, pas seulement de performance ou de métadonnées. Une chaîne de codecs valide en apparence pouvait écrire puis relire un tableau différent, ce qui est particulièrement préoccupant pour les grilles quantitatives.

**Action possible :** à tester. Ajouter un round-trip exact avec les filtres et l’ordre de transposition utilisés dans les jeux de données; attendre la prochaine release Zarr-Python avant de considérer le problème résolu dans un environnement publié.

**Sources primaires :**

- Pull request Zarr-Python #4558 : <https://github.com/zarr-developers/zarr-python/pull/4558>
- Commit fusionné : <https://github.com/zarr-developers/zarr-python/commit/d4d4d38b300204236014d0b2fb78b8aa8123dea9>
- Releases Zarr-Python : <https://github.com/zarr-developers/zarr-python/releases>

## 5. pyproj corrige `sync --system-directory` pour télécharger les grilles au bon endroit

**Date :** 16 novembre 2026  
**Statut :** correctif fusionné dans `main`; absent de la release pyproj 3.8.0 actuellement publiée  
**Importance pratique :** moyenne à élevée pour les transformations dépendant de grilles PROJ

`pyproj sync --system-directory` séparait les répertoires avec `os.path.sep` au lieu de `os.pathsep`. Sous Linux, la cible devenait vide; sous Windows, elle pouvait devenir seulement la lettre du lecteur. Les grilles et `files.geojson` étaient alors placés dans le répertoire courant au lieu du premier répertoire de données PROJ.

**Pourquoi ça concerne les praticiens :** la commande pouvait sembler réussir alors que PROJ ne trouvait ensuite pas la grille nécessaire à une transformation précise. Le problème touche directement la reproductibilité des environnements et peut faire choisir une opération de repli moins précise ou provoquer un échec.

**Action possible :** à vérifier. Contrôler l’emplacement réel des fichiers après `pyproj sync --system-directory` et tester une transformation qui dépend explicitement de la grille; utiliser un `--target-directory` validé comme mesure locale si nécessaire, puis attendre une release pyproj avec le correctif.

**Sources primaires :**

- Signalement pyproj #1672 : <https://github.com/pyproj4/pyproj/issues/1672>
- Pull request pyproj #1673 : <https://github.com/pyproj4/pyproj/pull/1673>
- Commit fusionné : <https://github.com/pyproj4/pyproj/commit/97e7de0ad0c8d0d804d714a26bf1cb654a7c1d6b>

## 6. Zarr corrige la migration v2→v3 des tableaux Blosc `AUTOSHUFFLE`

**Date :** 16 novembre 2026  
**Statut :** correctif fusionné dans `main`; absent de la release Zarr-Python 3.4.2 actuellement publiée  
**Importance pratique :** moyenne pour les migrations de magasins Zarr historiques

`zarr migrate v3` échouait sur un tableau Zarr v2 utilisant `Blosc.AUTOSHUFFLE`, car Numcodecs sérialise cette option comme `shuffle: -1` alors que le convertisseur v3 n’acceptait que 0 à 2. La migration traduit maintenant cette valeur en `bitshuffle` pour les éléments d’un octet et en `shuffle` pour les éléments plus grands, conformément au comportement de Numcodecs.

**Pourquoi ça concerne les praticiens :** des magasins v2 parfaitement lisibles pouvaient être impossibles à migrer automatiquement. Le correctif conserve aussi le mode de shuffle effectivement utilisé, ce qui évite de modifier silencieusement l’encodage lors de la réécriture de nouveaux chunks.

**Action possible :** à tester. Inventorier les métadonnées v2 contenant `shuffle: -1`, migrer une copie et comparer données, métadonnées et en-têtes Blosc avant toute migration en place; attendre une release Zarr-Python incluant le correctif.

**Sources primaires :**

- Pull request Zarr-Python #4630 : <https://github.com/zarr-developers/zarr-python/pull/4630>
- Commit fusionné : <https://github.com/zarr-developers/zarr-python/commit/13f75f7774861ad94ad83b6d4aa2e14e9eb78150>

Aucune autre nouveauté suffisamment significative n’a été confirmée depuis l’édition précédente pour GeoMet/ECCC, WMO/WIS2, MapServer, pygeoapi, NetCDF, xarray/Dask, kerchunk, OKF, MCP ou les modèles IA météo et géospatiale.
