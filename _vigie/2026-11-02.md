## 1. pygeoapi normalise le type média CoverageJSON dans les réponses et l’interface EDR

**Fusion : 1er novembre 2026 · Statut : changement fusionné dans `master`, pas encore publié dans une nouvelle version · Importance pratique : élevée pour les intégrations pygeoapi, EDR et Coverages.**

pygeoapi remplace `application/prs.coverage+json` par le type média normalisé `application/vnd.cov+json` dans l’en-tête `Content-Type` des réponses de couverture, les liens de collection et la détection du lien JSON dans le gabarit HTML. La pull request rattache ce choix à la clause 10 de la spécification OGC 21-069r2. Elle confirme aussi qu’une requête avec `Accept: application/vnd.cov+json` est correctement négociée.

Ce changement complète l’usage déjà présent du type `application/vnd.cov+json` dans certains liens EDR de pygeoapi 0.24.0; il ne constitue pas encore une nouvelle release. Il corrige surtout l’incohérence entre les métadonnées, l’en-tête de réponse et l’interface HTML.

**Pourquoi ça te concerne :** les clients GeoMet ou autres consommateurs d’OGC API qui valident strictement `Content-Type`, négocient le format avec `Accept`, indexent les liens par type média ou utilisent ce champ dans des caches et des tests contractuels peuvent observer un changement après une future mise à niveau de pygeoapi.

**Action : à tester et à préparer.** Ajouter un test avec `Accept: application/vnd.cov+json`, mettre à jour les assertions qui attendent encore `application/prs.coverage+json` et, si une transition est nécessaire, accepter temporairement les deux valeurs côté client. Attendre une version pygeoapi publiée avant de considérer ce comportement comme disponible dans une distribution stable.

**Sources primaires :** [geopython/pygeoapi — pull request #2477](https://github.com/geopython/pygeoapi/pull/2477) · [OGC 21-069r2, clause 10](https://docs.ogc.org/cs/21-069r2/21-069r2.html#_b8b17e78-0147-4b58-8ade-a19465b57abc) · [pygeoapi 0.24.0](https://github.com/geopython/pygeoapi/releases/tag/0.24.0).

## 2. GDAL protège ses typemaps SWIG contre des nettoyages sur pointeur nul

**Fusion : 1er novembre 2026 à 21:11 HNE (2 novembre à 02:11 UTC) · Statut : changement fusionné dans `master`, pas encore publié · Importance pratique : moyenne et conditionnelle.**

GDAL a ajouté des vérifications de pointeurs nuls aux typemaps `freearg` de ses bindings Python et Java. Le changement répond à une modification récente de SWIG `master` : lorsqu’un argument antérieur échoue à la conversion, le nettoyage peut désormais s’exécuter avant l’initialisation de certains arguments suivants. Sans garde, un typemap GDAL pouvait déréférencer un pointeur nul et provoquer un crash. Les responsables indiquent que les versions actuelles de SWIG ne sont pas affectées et que les garde-fous restent compatibles avec elles.

**Pourquoi ça te concerne :** l’impact se situe dans la chaîne de compilation plutôt que dans les traitements raster ou vectoriels eux-mêmes. Une image ou un paquet construit directement contre SWIG `master` peut rencontrer ce problème lors d’un appel Python invalide; rien dans la source ne montre que les binaires GDAL publiés actuels sont touchés.

**Action : à suivre; à tester seulement pour les builds de pointe.** Si une chaîne CI compile GDAL contre SWIG `master`, utiliser un commit GDAL contenant le correctif ou épingler temporairement SWIG, puis ajouter des tests négatifs de conversion d’arguments. Aucune modification de production n’est justifiée pour les distributions stables sur la seule base de cette fusion; attendre une release GDAL qui l’inclut.

**Sources primaires :** [OSGeo/GDAL — pull request #15463](https://github.com/OSGeo/gdal/pull/15463) · [SWIG — changement de nettoyage des arguments](https://github.com/swig/swig/commit/f8cf11b7209c03c5154ffb738f1650c2631027c3).
