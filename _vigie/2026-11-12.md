Sept changements dépassent aujourd’hui le seuil de publication. Tous les correctifs logiciels ci-dessous sont fusionnés mais absents des versions stables actuelles; l’annonce MCP décrit un calendrier de travail et ne constitue pas une nouvelle version du protocole.

## 1. GDAL corrige un dépassement de tampon dans HDF-EOS

**Date :** signalé le 6 novembre; correctif fusionné le 12 novembre 2026  
**Statut :** correctif fusionné dans `master`; aucune release ni CVE annoncé  
**Importance pratique :** élevée lorsque des fichiers HDF-EOS/HDF4 externes sont ouverts

`SWgetfillvalue()` et `GDgetfillvalue()` construisaient le nom d’un attribut dans un tampon de 80 caractères avec `strcat()`. Un `DataFieldName` suffisamment long, fourni par les métadonnées du fichier, pouvait déborder la pile dès l’ouverture. Le rapporteur reproduit le problème avec un fichier HDF-EOS2 valide et `gdalinfo`, sous GDAL 3.8.4 et une version 3.14 de développement. Le correctif remplace les concaténations et augmente le tampon pour correspondre au code amont.

**Pourquoi ça te concerne :** HDF4/HDF-EOS peut entrer dans une chaîne de conversion ou de catalogage scientifique. Le défaut se déclenche pendant l’ouverture, avant qu’une validation métier ou une extraction raster puisse protéger le processus.

**Action possible :** continuer d’isoler les fichiers non fiables et ajouter le fichier de reproduction aux tests d’ingestion. Suivre la prochaine release GDAL; les installations stables actuelles ne contiennent pas encore le commit.

**Sources primaires :**

- Issue GDAL #15486 : <https://github.com/OSGeo/gdal/issues/15486>
- Pull request fusionnée #15497 : <https://github.com/OSGeo/gdal/pull/15497>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/687ad8d5c122c63982deea735486e42f3ac8682e>

## 2. Le correctif GDAL/HDF5 suivi hier est maintenant fusionné

**Date :** 12 novembre 2026  
**Statut :** correctif fusionné dans `master`; aucune release ni CVE annoncé  
**Importance pratique :** élevée pour les chaînes ouvrant des fichiers HDF5 externes

GDAL vérifie maintenant l’échec de `H5Aread()` avant de concaténer ou libérer des chaînes HDF5 de longueur variable. Cela ferme le chemin où un pointeur non initialisé pouvait être interprété après l’échec de lecture d’un attribut. La pull request était encore ouverte dans l’édition du 11 novembre.

**Pourquoi ça te concerne :** les métadonnées HDF5 et NetCDF sont lues très tôt dans les pipelines météo et climat. Le changement réduit un risque de crash ou de lecture mémoire invalide sur des entrées atypiques ou non fiables.

**Action possible :** rejouer le fichier minimal dans une image construite depuis le commit, puis attendre une release avant de considérer les environnements distribués comme corrigés.

**Sources primaires :**

- Pull request GDAL #15500 : <https://github.com/OSGeo/gdal/pull/15500>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/bd20a68c30446ac800b7bfdbee3857571e3aee02>

## 3. GDAL corrige le faux négatif GeoParquet `Point Z`

**Date :** 12 novembre 2026  
**Statut :** correctif fusionné dans `master`; pas encore publié  
**Importance pratique :** moyenne pour les validations GeoParquet 3D

Le validateur associe désormais correctement `ogr.wkbPoint25D` à `Point Z`. Un fichier que GDAL écrivait avec `geometry_types: ["Point Z"]` ne devrait donc plus être rejeté par son propre validateur. Le problème était encore ouvert dans l’édition précédente.

**Pourquoi ça te concerne :** les contrôles CI pourront distinguer une vraie non-conformité d’un faux négatif du validateur, sans bloquer inutilement une publication GeoParquet 3D valide.

**Action possible :** conserver un test de bout en bout écriture → validation avec `Point Z`, puis retirer toute exception temporaire seulement après adoption d’une release contenant le correctif.

**Sources primaires :**

- Pull request GDAL #15517 : <https://github.com/OSGeo/gdal/pull/15517>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/7b845fc3216ccac920940642352b97ef26a18410>

## 4. OGR harmonise le filtrage spatial GeoPackage entre Arrow et l’API classique

**Date :** 12 novembre 2026  
**Statut :** correctif fusionné dans `master`; pas encore publié  
**Importance pratique :** moyenne pour les pipelines GeoPackage → Arrow

Avec un filtre spatial couvrant toute l’emprise d’une couche, `GetArrowStream()` pouvait conserver les entités dont la géométrie était `NULL`, alors que `GetNextFeature()` les excluait conformément au contrat OGR. Le chemin utilisant un filtre plus petit et l’index R-tree ne présentait pas cette divergence. Le correctif ignore maintenant les géométries nulles dès qu’un filtre spatial est actif.

**Pourquoi ça te concerne :** deux chemins de lecture d’une même couche pouvaient produire des nombres d’entités différents, ce qui fragilise les tests, statistiques et conversions cloud-native basées sur Arrow.

**Action possible :** ajouter un test comparatif Arrow/API classique avec géométries `NULL` et `EMPTY`, pour un filtre couvrant l’emprise et pour un filtre plus petit.

**Sources primaires :**

- Pull request GDAL #15470 : <https://github.com/OSGeo/gdal/pull/15470>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/c5d794fe0c8feae8bf5ab9c19094b3826e5d458f>

## 5. PROJ corrige la conversion décimètre → mètre

**Date :** 11 novembre 2026  
**Statut :** correctif fusionné dans `master`; pas encore publié  
**Importance pratique :** moyenne lorsque des CRS ou opérations emploient explicitement le décimètre

La base PROJ déclarait `1 dm = 0,01 m` au lieu de `0,1 m`, soit une erreur d’un facteur dix. Selon la pull request, cette valeur était présente depuis au moins six ans. Le correctif met à jour la base générée et les tests associés.

**Pourquoi ça te concerne :** les transformations ordinaires en mètres ou degrés ne changent pas, mais tout CRS ou paramètre exprimé en décimètres pouvait être mis à l’échelle incorrectement. pyproj hérite de cette base PROJ.

**Action possible :** rechercher l’unité `decimetre`/`decimeter` dans les CRS et opérations réellement utilisés. Si elle apparaît, comparer les résultats avant et après le commit; sinon, aucune action immédiate.

**Sources primaires :**

- Pull request PROJ #4943 : <https://github.com/OSGeo/PROJ/pull/4943>
- Commit fusionné : <https://github.com/OSGeo/PROJ/commit/890f8a0599ee4600344c8b630df5e4bc4762c83f>

## 6. MCP adopte un cycle prévisible de deux versions par année

**Date :** 11 novembre 2026  
**Statut :** calendrier officiel; aucune nouvelle version normative  
**Importance pratique :** moyenne pour planifier les implémentations et tests d’interopérabilité

MCP prévoit maintenant une version de spécification tous les six mois, généralement le dernier mardi de mars et de septembre. La prochaine cible est le 30 mars 2027, avec l’identifiant prévu `2027-03-30`; les échéances de propositions et les bêtas des SDK doivent être publiées en amont.

**Pourquoi ça te concerne :** un calendrier connu permet d’aligner les serveurs MCP donnant accès à des API météo/géospatiales, les tests de compatibilité et les revues de sécurité sur des jalons explicites plutôt que sur des changements continus difficiles à figer.

**Action possible :** suivre les fenêtres de propositions et planifier une validation protocole/SDK avant mars 2027. Aucun changement de production n’est requis par cette annonce seule.

**Sources primaires :**

- Annonce MCP : <https://blog.modelcontextprotocol.io/posts/mcp-release-cycle/>
- Pull request de publication #3541 : <https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3541>

## 7. `zarr-metadata` change les valeurs dérivées par `create_default()`

**Date :** 12 novembre 2026  
**Statut :** changement incompatible fusionné dans le sous-projet; aucune release publiée  
**Importance pratique :** moyenne pour les générateurs et validateurs de métadonnées Zarr

`create_default()` dérive maintenant le fill value, le codec tableau→octets et certains chunks à partir du type et de la forme fournis. Par exemple, les chaînes Zarr V3 reçoivent `vlen-utf8`, les octets `vlen-bytes`, les types temporels `NaT`, et une dimension de longueur zéro reçoit un chunk de longueur 1 en V2. Certains documents qui échouaient pourront être créés, tandis que les valeurs sérialisées par défaut changent.

**Pourquoi ça te concerne :** un agent ou catalogue qui fabrique des métadonnées machine-actionable peut produire un document différent sans modifier son appel. Cela affecte les tests byte-for-byte, les hypothèses sur les fill values et l’interopérabilité des types variables.

**Action possible :** épingler `zarr-metadata`, tester chaque dtype météo utilisé et comparer les documents JSON générés avant/après. Attendre une release et lire son changelog avant mise à niveau.

**Sources primaires :**

- Pull request zarr-python #4621 : <https://github.com/zarr-developers/zarr-python/pull/4621>
- Commit fusionné : <https://github.com/zarr-developers/zarr-python/commit/923498db4175f9a3d8dcca8b0e416d1193e267cf>

Aucun nouveau changement suffisamment significatif n’a été confirmé aujourd’hui pour GeoMet/ECCC, WIS2, OGC, MapServer, pygeoapi, xarray/Dask, kerchunk, OKF ou les modèles IA météo.
