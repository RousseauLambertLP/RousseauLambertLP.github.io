Cinq changements méritent une attention pratique. L’avis GeoDjango du 3 novembre est inclus aujourd’hui parce que ses deux vecteurs CRS/GDAL touchent directement la sécurité des services géospatiaux et n’avaient pas été retenus dans les éditions précédentes. Les quatre autres changements ont été fusionnés le 6 novembre, mais ne sont pas encore des releases. Aucun nouveau développement suffisamment significatif n’a été confirmé pour GeoMet, WIS2, MapServer, PROJ/pyproj, OGC, OKF ou l’IA météo.

## 1. GeoDjango corrige deux vecteurs SSRF et de lecture locale liés aux CRS

**Date :** 3 novembre 2026  
**Statut :** versions de sécurité Django 6.1.3, 6.0.10 et 5.2.19 publiées  
**Importance pratique :** élevée pour toute API acceptant des géométries ou des CRS non fiables

Deux avis concernent directement la pile géospatiale. CVE-2026-111362 corrige l’acceptation, dans des géométries GeoJSON, de références CRS externes que GDAL pouvait résoudre par accès réseau ou fichier. CVE-2026-114582 touche les chaînes transmises à `SpatialReference`, aux méthodes `transform()` et à plusieurs setters `srs`/`srid`, qui pouvaient également provoquer des requêtes sortantes ou lire des fichiers locaux.

Django qualifie le premier avis de sévérité modérée et le second de faible. La protection complète de `SpatialReference` exige GDAL 3.9 ou plus récent; sur une version GDAL antérieure, Django recommande des SRID entiers ou une liste d’autorisation pour les chaînes. Le nouveau contrôle système `gis.W001` avertit lorsque GDAL est trop ancien.

**Pourquoi ça te concerne :** une API météo ou géospatiale peut recevoir des géométries, des CRS ou des paramètres de reprojection. Même sans utiliser GeoDjango dans GeoMet, ces avis illustrent le risque de laisser une bibliothèque géospatiale résoudre implicitement des URL ou des chemins fournis par un client.

**Action possible :** inventorier les services Django GIS, mettre à jour vers une version corrigée, vérifier que GDAL est au moins en 3.9 et exécuter les contrôles système. Pour toute autre API, préférer des identifiants CRS validés sur liste plutôt que des définitions arbitraires provenant du réseau.

**Sources primaires :**

- Annonce de sécurité Django : <https://www.djangoproject.com/weblog/2026/nov/03/security-releases/>
- Notes Django 6.1.3 : <https://docs.djangoproject.com/en/6.1/releases/6.1.3/>

## 2. pygeoapi corrige une course dans les callbacks OGC API — Processes

**Date :** 6 novembre 2026  
**Statut :** changement fusionné dans `master`, pas encore publié dans une release  
**Importance pratique :** élevée pour les déploiements utilisant les abonnés de processus

Le gestionnaire de processus conservait le processeur courant dans une propriété partagée. Des exécutions concurrentes pouvaient donc se remplacer mutuellement. Le correctif garde désormais le processeur dans une variable locale et transmet explicitement son paramètre `allow_internal_requests` aux notifications `inProgressUri`, `successUri` et `failedUri`. Une URL d’abonné interdite renvoie maintenant une erreur HTTP 400 dédiée.

**Pourquoi ça te concerne :** les callbacks de jobs asynchrones se trouvent à une frontière SSRF sensible. Une décision d’autoriser ou non une adresse interne doit appartenir au processus réellement exécuté, sans dépendre d’un état mutable partagé entre requêtes.

**Action possible :** ajouter un test concurrent couvrant deux processus ayant des politiques d’accès interne différentes, ainsi que des callbacks vers loopback et plages privées. Attendre une release pygeoapi contenant le commit avant de considérer les installations distribuées comme corrigées.

**Sources :**

- Pull request pygeoapi #2479 : <https://github.com/geopython/pygeoapi/pull/2479>
- Commit fusionné : <https://github.com/geopython/pygeoapi/commit/133f077e11ffdd966c2f0117b7adcb1dca30f132>

## 3. GDAL corrige un use-after-free dans `Geometry.AddGeometryDirectly()`

**Date :** 6 novembre 2026  
**Statut :** correctif fusionné dans `master`, pas encore publié dans une version GDAL  
**Importance pratique :** moyenne à élevée pour le code Python OGR manipulant la propriété des géométries

Les bindings Python ne conservaient pas correctement la relation de propriété lorsqu’une sous-géométrie était transférée avec `AddGeometryDirectly()`. Après la destruction du parent ou de la feature, le wrapper Python de la sous-géométrie pouvait encore référencer de la mémoire libérée. Le correctif enregistre désormais le parent et la référence transférée, avec des tests de durée de vie.

**Pourquoi ça te concerne :** les ETL géospatiaux qui assemblent des anneaux, polygones ou géométries composées en Python peuvent subir un crash ou un comportement indéfini selon l’ordre de collecte des objets. Ce n’est pas présenté comme un CVE ni comme une vulnérabilité exploitable à distance.

**Action possible :** ajouter un test qui détruit explicitement le parent après `AddGeometryDirectly()`, puis vérifie le comportement de la sous-géométrie. Attendre une release GDAL contenant le correctif; éviter entre-temps de réutiliser un objet dont la propriété a été transférée.

**Sources :**

- Pull request GDAL #15466 : <https://github.com/OSGeo/gdal/pull/15466>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/a9678354d99f44466a93dbc68fcd80b78a7fc355>

## 4. MCP documente et corrige un piège de validation `oneOf` dans les schémas d’outils

**Date :** 6 novembre 2026  
**Statut :** exemples et documentation fusionnés dans la révision courante 2026-07-28 et le brouillon; pas une nouvelle version normative  
**Importance pratique :** moyenne pour les outils d’agents à entrées structurées

L’exemple `find_resource` plaçait les définitions de propriétés et leurs types à l’intérieur de branches `oneOf`. Une requête contenant les deux propriétés pouvait alors rendre une branche non applicable en donnant un type erroné à l’une d’elles, et être acceptée par l’autre branche. Le correctif place les `properties` à la racine et réserve `oneOf` aux assertions de présence avec `required`. La documentation précise désormais ce piège d’écriture JSON Schema.

**Pourquoi ça te concerne :** des outils d’agents qui appellent des API météo ou géospatiales doivent valider les identifiants, étendues et options avant l’exécution. Un schéma apparemment strict peut accepter une combinaison mal typée si les contraintes de type sont enfermées dans les branches de composition.

**Action possible :** tester les schémas MCP utilisant `oneOf`, `anyOf` ou `allOf` avec des propriétés simultanées et volontairement mal typées. Conserver les types communs à la racine et utiliser les branches pour les contraintes conditionnelles.

**Sources :**

- Pull request MCP #3185 : <https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3185>
- Commit fusionné : <https://github.com/modelcontextprotocol/modelcontextprotocol/commit/38353251fab3bdeead03dd8283b9e66076ce1a7f>

## 5. Zarr-Python corrige l’indexation orthogonale avec tableau suivi de `...`

**Date :** 6 novembre 2026  
**Statut :** correctif fusionné dans `main`, pas encore publié  
**Importance pratique :** moyenne pour les sélections de cubes multidimensionnels

Une sélection comme `z.oindex[[1, 2], ...]` échouait parce que Zarr comparait `Ellipsis` à un tableau NumPy avec `==`, ce qui produit un tableau booléen dont la valeur de vérité est ambiguë. Le correctif compare désormais l’ellipse par identité et couvre les tableaux d’indices entiers et les masques booléens, en lecture comme en écriture.

**Pourquoi ça te concerne :** cette syntaxe est naturelle pour extraire un sous-ensemble de stations, niveaux ou échéances tout en conservant les dimensions restantes d’un cube météo. L’erreur peut apparaître indépendamment du contenu des données.

**Action possible :** ajouter des tests `oindex` avec listes, tableaux NumPy, masques booléens et ellipse en lecture/écriture. Attendre une release Zarr-Python intégrant le commit avant la mise à niveau de production.

**Sources :**

- Pull request Zarr-Python #4595 : <https://github.com/zarr-developers/zarr-python/pull/4595>
- Commit fusionné : <https://github.com/zarr-developers/zarr-python/commit/659531808ee2e98435dc6e3a33f846970b5f269d>
