Trois changements de code fusionnés depuis l’édition précédente dépassent le seuil de publication. Ils ne constituent pas encore des versions publiées : il faut donc les suivre ou les tester sur les branches de développement, sans présumer de leur présence dans les paquets stables.

## 1. Zarr-Python lit les noms abrégés d’extensions autorisés par Zarr V3.1

**Date :** 8 novembre 2026  
**Statut :** correctif fusionné dans la branche principale de zarr-python; aucune nouvelle version publiée  
**Importance pratique :** élevée pour l’interopérabilité des cubes de données Zarr V3.1

Zarr V3.1 permet de représenter certaines extensions sans configuration par un simple nom, par exemple `"crc32c"`, plutôt que par l’objet `{"name": "crc32c"}`. Zarr-Python pouvait toutefois rejeter ces métadonnées valides avec une erreur de type. Le correctif développe maintenant ces formes abrégées pour les codecs, y compris dans le sharding imbriqué, le `chunk grid`, le `chunk-key encoding` et les `storage transformers`. Les extensions qui exigent une configuration restent refusées lorsqu’elle manque.

Pour conserver la compatibilité avec les lecteurs V3.0, Zarr-Python continue d’écrire la forme objet plutôt que la forme abrégée.

**Pourquoi ça te concerne :** un cube météo produit par un autre writer conforme à Zarr V3.1 peut être valide tout en restant illisible avec une version actuelle de zarr-python. C’est un cas d’interopérabilité concret pour les chaînes cloud-native et les traitements xarray/Dask.

**Action possible :** ajouter des fixtures de compatibilité contenant des codecs abrégés, du sharding imbriqué et un `chunk_key_encoding` abrégé; suivre la prochaine release zarr-python avant d’en dépendre en production.

**Sources primaires :**

- Pull request zarr-python #4506 : <https://github.com/zarr-developers/zarr-python/pull/4506>
- Commit fusionné : <https://github.com/zarr-developers/zarr-python/commit/e6658d22c282d96641af1e3779bfb47c66d9ead7>

## 2. `zarr-metadata` ajoute un précontrôle pour savoir si un nœud V3 est réellement ouvrable

**Date :** 8 novembre 2026  
**Statut :** fonctionnalité fusionnée dans le sous-projet `zarr-metadata`; aucune version publiée  
**Importance pratique :** moyenne à élevée pour les pipelines automatisés, catalogues et agents

Le nouveau lecteur `read_openable_node_metadata_v3` signale les déclarations qu’un lecteur ne sait pas interpréter : codec, type de données ou `chunk grid` inconnu, ainsi que membre de premier niveau inconnu qui n’est pas explicitement marqué `"must_understand": false`. Les lecteurs généraux restent permissifs afin de préserver l’extensibilité du format.

**Pourquoi ça te concerne :** ce contrôle distingue des métadonnées JSON valides d’un jeu de données réellement ouvrable par un environnement donné. Un catalogue, un pipeline ETL ou un agent peut donc détecter une incompatibilité avant de lancer un calcul Dask coûteux ou d’annoncer à tort qu’une ressource est exploitable.

**Action possible :** prototyper ce lecteur comme étape de prévalidation et conserver les déclarations non reconnues dans un diagnostic structuré; ne pas le considérer comme disponible dans une version stable avant sa publication.

**Sources primaires :**

- Pull request zarr-python #4604 : <https://github.com/zarr-developers/zarr-python/pull/4604>
- Commit fusionné : <https://github.com/zarr-developers/zarr-python/commit/f50cce1300cc76203757c503cc9af92e6d1f2203>

## 3. GDAL initialise correctement l’ordinal d’un champ FID également exposé comme attribut SQLite

**Date :** 8 novembre 2026  
**Statut :** correctif fusionné dans la branche principale de GDAL; aucune nouvelle version publiée  
**Importance pratique :** moyenne, mais limitée aux schémas OGR/SQLite concernés

Dans `OGRSQLiteTableLayer::RecomputeOrdinals()`, l’ordinal d’un champ FID également créé comme champ régulier n’était pas initialisé avant l’incrément du compteur. Le défaut a été trouvé avec MemorySanitizer. Le correctif initialise l’ordinal et ajoute un test vérifiant simultanément le FID, le champ FID régulier et les attributs voisins.

**Pourquoi ça te concerne :** ce cas étroit peut affecter la correspondance entre colonnes et attributs lors de la lecture de tables SQLite qui exposent leur identifiant comme champ normal. Les services ou conversions qui s’appuient sur OGR doivent pouvoir faire confiance à cette correspondance.

**Action possible :** ajouter un test de régression ouvrant une couche SQLite dont le FID est aussi un attribut et comparer le FID, ce champ et les colonnes voisines; attendre une release GDAL avant de supposer le correctif présent dans les distributions.

**Sources primaires :**

- Issue/patch GDAL #15490 : <https://github.com/OSGeo/gdal/issues/15490>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/15c79ff06cbc32a6631bdf303b956aa7210c7ad3>
