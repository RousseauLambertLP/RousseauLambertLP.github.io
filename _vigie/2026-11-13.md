Sept changements récents dépassent aujourd’hui le seuil de publication. Tous sont fusionnés dans les branches de développement, mais aucun n’est encore inclus dans une version stable annoncée.

## 1. MapServer corrige une confusion de type causant un `heap-buffer-overflow`

**Date :** 12 novembre 2026  
**Statut :** correctif fusionné dans `main`; aucun CVE ni release annoncé  
**Importance pratique :** élevée pour les services qui acceptent des filtres OGC externes

Un littéral `PropertyIsEqualTo` dont la valeur était `PropertyIsLike` pouvait être interprété et libéré comme un nœud `FEPropertyIsLike`, provoquant un dépassement de tampon sur le tas. Le défaut a été trouvé par OSS-Fuzz. Le correctif vérifie maintenant le type du nœud en plus de sa valeur textuelle.

**Pourquoi ça te concerne :** WMS/WFS et autres interfaces acceptant des expressions Filter Encoding peuvent traiter des documents contrôlés par un client. Une entrée mal formée ne devrait pas pouvoir faire tomber le processus MapServer.

**Action possible :** suivre le backport vers la branche 8.6 et la prochaine release corrective. Ajouter le cas OSS-Fuzz aux tests d’entrée non fiable; ne pas présenter les versions stables actuelles comme corrigées.

**Sources primaires :**

- Pull request MapServer #7679 : <https://github.com/MapServer/MapServer/pull/7679>
- Commit fusionné : <https://github.com/MapServer/MapServer/commit/884a4f19681a6bb157496685d41b0944e8833c32>
- Proposition de backport 8.6 : <https://github.com/MapServer/MapServer/pull/7688>

## 2. GDAL ferme une fuite d’information malgré `ALLOW_FILE_ACCESS=NO`

**Date :** 12 novembre 2026  
**Statut :** correctif fusionné dans `master`; pas encore publié  
**Importance pratique :** élevée pour les API qui valident des CRS fournis par un client

`SetFromUserInput()` pouvait encore appeler `stat()` sur un chemin lorsque `ALLOW_FILE_ACCESS=NO` était actif. Les codes d’erreur différaient selon que le fichier existait ou non, permettant de sonder le système de fichiers. Le correctif ne touche plus au chemin et renvoie désormais un résultat uniforme.

**Pourquoi ça te concerne :** la validation de CRS est une frontière d’entrée fréquente dans les API géospatiales. Désactiver la lecture de fichiers doit également empêcher la divulgation de leur présence.

**Action possible :** ajouter des tests comparant chemins existants et inexistants, puis adopter une release contenant le correctif. Ce changement récent n’avait pas été retenu dans l’édition précédente.

**Sources primaires :**

- Issue GDAL #15479 : <https://github.com/OSGeo/gdal/issues/15479>
- Pull request fusionnée #15499 : <https://github.com/OSGeo/gdal/pull/15499>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/696d7438467908f8468739ce24af83c2fc91a25f>

## 3. GDAL corrige les valeurs d’attributs HDF5 multidimensionnels

**Date :** 12 novembre 2026  
**Statut :** correctif fusionné dans `master`; pas encore publié  
**Importance pratique :** élevée pour les métadonnées HDF5/NetCDF multidimensionnelles

L’API multidimensionnelle avançait le pointeur source d’un seul élément à chaque dimension au lieu d’utiliser le stride de la dimension. Un attribut 2 × 3 contenant `0…5` pouvait ainsi être lu comme `0,1,2,1,2,3`. `gdalinfo` classique n’était pas touché, mais `gdalmdiminfo` et l’API multidimensionnelle retournaient de mauvaises valeurs.

**Pourquoi ça te concerne :** des attributs scientifiques peuvent piloter les unités, les axes, la qualité ou l’interprétation d’un cube météo. Une lecture silencieusement incorrecte est plus dangereuse qu’un échec explicite.

**Action possible :** tester des attributs 2D et 3D non triviaux dans les validations HDF5/NetCDF et comparer API classique, API multidimensionnelle et h5py.

**Sources primaires :**

- Pull request GDAL #15509 : <https://github.com/OSGeo/gdal/pull/15509>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/2e13e4b82ac38020ed7dc7a98a4c4ced7226c415>

## 4. xarray partage les handles HDF5 ouverts en lecture seule

**Date :** 12 novembre 2026  
**Statut :** changement fusionné; pas encore publié  
**Importance pratique :** moyenne à élevée pour les traitements ouvrant plusieurs groupes ou variables d’un même fichier

xarray réutilise maintenant un handle HDF5 pour des ouvertures locales identiques en lecture seule avec `h5netcdf` ou `netCDF4`, jusqu’à la fermeture du dernier dataset. Les modes écriture et NetCDF3 conservent leur comportement. Le changement couvre aussi les verrous, le pickling et les workers distribués.

**Pourquoi ça te concerne :** des traitements météo ouvrant plusieurs groupes d’un même NetCDF4 pouvaient multiplier les handles, faire thrash le cache de fichiers et exposer des interactions fragiles avec HDF5.

**Action possible :** à tester avec les patrons réels d’ouverture multi-groupes, Dask distribué et fermeture explicite. Mesurer les handles et la mémoire avant/après; attendre une release avant déploiement.

**Sources primaires :**

- Pull request xarray #11809 : <https://github.com/pydata/xarray/pull/11809>
- Commit fusionné : <https://github.com/pydata/xarray/commit/819c63708617f47cc271229a45a753dbe43c0451>

## 5. GDAL ajoute `gdal crs info`

**Date :** 12 novembre 2026  
**Statut :** fonctionnalité fusionnée dans `master`; pas encore publiée  
**Importance pratique :** moyenne pour l’inspection et la validation automatisées des CRS

La nouvelle commande porte les capacités de `gdalsrsinfo` dans la CLI unifiée : validation, identification EPSG et sorties WKT, PROJJSON, PROJ.4, MapInfo ou XML. Elle prend aussi en charge l’aide structurée `--json-usage`.

**Pourquoi ça te concerne :** elle simplifie les diagnostics reproductibles autour des CRS dans les pipelines et peut fournir une interface plus cohérente à des outils ou agents que l’ancien exécutable séparé.

**Action possible :** préparer des tests de parité avec `gdalsrsinfo`, notamment pour `--validate`, `--identify` et PROJJSON. Ne pas modifier les scripts de production avant une release intégrant la commande.

**Sources primaires :**

- Pull request GDAL #15441 : <https://github.com/OSGeo/gdal/pull/15441>
- Commit fusionné : <https://github.com/OSGeo/gdal/commit/a077f4a553b53bb2d1364259d3018201d11f882a>

## 6. MapServer stabilise le rendu des jointures presque colinéaires

**Date :** 13 novembre 2026  
**Statut :** correctif fusionné dans `main`; pas encore publié  
**Importance pratique :** moyenne pour la cartographie dynamique

Pour certaines jointures externes entre segments presque parallèles, le calcul AGG pouvait placer le point d’intersection à des millions de pixels. MapServer revient maintenant au point décalé simple lorsque l’intersection dépasse `width × miter_limit`.

**Pourquoi ça te concerne :** une géométrie valide mais numériquement défavorable pouvait produire un rendu pathologique, une image démesurée ou un coût de traitement disproportionné dans un service cartographique météo.

**Action possible :** conserver un cas de régression avec lignes presque colinéaires et surveiller le backport 8.6 avant mise à niveau.

**Sources primaires :**

- Pull request MapServer #7683 : <https://github.com/MapServer/MapServer/pull/7683>
- Commit fusionné : <https://github.com/MapServer/MapServer/commit/499756acc8f644592b7017ea1975cb8e10ffe3d9>
- Proposition de backport 8.6 : <https://github.com/MapServer/MapServer/pull/7690>

## 7. `zarr-metadata` rend les définitions de codecs plus strictes

**Date :** 12 novembre 2026  
**Statut :** changement incompatible fusionné; changelog 0.8.0 préparé, mais aucune release confirmée  
**Importance pratique :** moyenne pour les validateurs et générateurs de métadonnées Zarr V3

Les codecs V3 sont maintenant représentés par des classes distinctes selon leur transition — tableau→tableau, tableau→octets ou octets→octets — plutôt que par `CodecDefinition(kind=...)`. Les types déclarent aussi une `number_class`, utilisée pour refuser plus tôt des combinaisons invalides, par exemple `scale_offset` avec une chaîne.

**Pourquoi ça te concerne :** les outils qui transforment des règles de format en validation machine-actionable peuvent détecter des pipelines codec/dtype impossibles avant d’accéder aux chunks. L’API Python change toutefois de manière incompatible.

**Action possible :** épingler la dépendance et tester les codecs réellement utilisés par les cubes météo. Préparer la migration des constructions `CodecDefinition(kind=...)`, puis attendre la publication 0.8.0.

**Sources primaires :**

- Pull request zarr-python #4628 : <https://github.com/zarr-developers/zarr-python/pull/4628>
- Commit fusionné : <https://github.com/zarr-developers/zarr-python/commit/4dc5b01a5810d8a23f57826320896d1b165e9537>
- Changelog 0.8.0 préparé : <https://github.com/zarr-developers/zarr-python/pull/4629>

Aucun nouveau changement suffisamment significatif n’a été confirmé aujourd’hui pour GeoMet/ECCC, WIS2, OGC, PROJ/pyproj, pygeoapi, Dask, kerchunk, OKF ou les modèles IA météo et géospatiale.
