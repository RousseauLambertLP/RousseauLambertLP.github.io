## 1. MCP servers 2.2.0: compromised certificates removed and new security fixes

**Published: October 28, 2026 · Status: version 2.2.0 published · Practical importance: high for deployments of the official MCP servers.**

Version **2.2.0** of `modelcontextprotocol/servers` updates the `certifi` bundle in the `mcp-server-fetch` container after eMudhra disclosed that private keys could be recovered for eight intermediate certificates. `certifi 2026.10.23` removes the `emSign Root CA - C1` and `emSign ECC Root CA - C3` roots. Recent PyPI installations resolve the current `certifi`, but an environment created before October 23 may retain the older bundle.

The release also publishes `mcp-server-fetch 2026.10.28`, including rejection of IPv4-compatible IPv6 destinations, a safer policy when `robots.txt` returns a 5xx error, and several HTML-extraction fixes. For the TypeScript servers, TLS validation depends on the Node.js runtime; the notes recommend Node.js **24.22.1**, **26.12.1**, or later.

**Why it matters:** a Fetch server retrieving documentation, catalogues or weather APIs sits on a sensitive network boundary. TLS trust and SSRF protections are part of the agent security model, independently of the language model's quality.

**Action: update.** Check the repository or package version, refresh existing `mcp-server-fetch` environments with `uvx --refresh` or update `certifi`, and verify the actual Node.js version used by TypeScript servers. An `engines: node 24` constraint alone does not guarantee a patched runtime.

**Primary source:** [modelcontextprotocol/servers — version 2.2.0](https://github.com/modelcontextprotocol/servers/releases/tag/v2.2.0).

## 2. MCP: forced tool selection can defeat the intent of annotations

**Opened: November 1, 2026 · Status: open clarification request, not a confirmed vulnerability or a specification change · Practical importance: high when designing agents with write-capable tools.**

An MCP specification issue notes that `readOnlyHint` and `destructiveHint` are explicitly untrusted when received from an untrusted server, but the specification does not fully explain how a client should compose a tool subset when the model API forces a tool call. The author reports **460 write calls in 816 trials** with mock tools when a call was forced, compared with **5 in 816** without that constraint; limiting the set to authorized tool classes produced no writes in those trials.

These are the author's results across four hosted models and have not been independently validated by MCP maintainers. The discussion nevertheless recognizes the conceptual issue: nothing received from an untrusted server should widen the set of tools that a client is willing to force.

**Why it matters:** an agent exposing read and mutation tools for APIs or data may select a write operation simply because the expected read tool is absent from the presented subset. Annotations are hints, not an authorization mechanism.

**Action: test and harden.** Separate read and write tools through local policy, construct the authorized tool list before any forced selection, and refuse or fall back to tool-free generation when that list is empty. Do not base write authorization on annotations supplied by an untrusted server.

**Primary sources:** [MCP issue #3492](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/3492) · [MCP specification — Tool annotations](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#tool).

## 3. xarray: automatic opening of Zarr directories fixed on Windows

**Merged: October 31, 2026 · Status: fix merged into `main`, not yet included in an xarray release · Practical importance: medium for Zarr processing on Windows.**

xarray attempted to read a magic number during engine detection. On Windows, opening a Zarr directory this way can raise `PermissionError` rather than `IsADirectoryError`, stopping `open_dataset()` before the Zarr backend can inspect the store. The merged fix first checks whether the path is a directory; tests cover Zarr formats 2 and 3 with both `str` and `Path` paths.

**Why it matters:** notebooks, development workstations and local Windows pipelines can fail to open a valid Zarr store even when the same data works elsewhere. This fix reduces a cross-platform behavior difference, but it is not yet available in a published release.

**Action: monitor.** Keep an automatic-open test for a local Zarr directory in the Windows matrix and wait for the next xarray release containing the commit. Explicitly setting `engine="zarr"` can be evaluated as a local workaround, without presenting it as the upstream fix.

**Primary source:** [pydata/xarray — pull request #11802](https://github.com/pydata/xarray/pull/11802).

## 4. OKF: proposal to prevent an agent from confirming its own output

**Opened: October 31, 2026 · Status: open proposal in the canonical repository, not merged into OKF v0.2 · Practical importance: monitor for agent-maintained knowledge.**

OKF v0.2 currently classifies a concept as `machine-confirmed` when it contains a `verified` event from a non-human actor. A new proposal observes that the agent named in `generated.by` can also add itself to `verified`, reaching that tier without an independent check. It proposes that consumers ignore, when calculating the trust tier, a verification from the same non-human producer.

This is a community proposal: the specification **has not changed** and no new version has been published.

**Why it matters:** an agent-usable weather rules or knowledge base must distinguish generation, deterministic validation and independent review. A trust label loses value when the same agent can both produce and confirm the content.

**Action: apply as a prototype rule, not an OKF requirement.** Use distinct producer identities for generation and verification, retain deterministic-check results, and do not present this rule as normative unless it is merged and versioned.

**Primary sources:** [OKF proposal #60](https://github.com/GoogleCloudPlatform/open-knowledge-format/issues/60) · [canonical OKF v0.2 specification](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md).
