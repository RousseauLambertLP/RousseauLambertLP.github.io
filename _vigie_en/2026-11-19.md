Seven changes clear the publication threshold. The MCP, xarray, and GDAL items are merged code changes, not yet stable releases. OKF’s canonical move and OpenAI’s data-residency feature were announced on November 18. PARDIG and SatWeave, published on November 13, are included as a dated catch-up because of their direct relevance to cloud-native weather data and AI.

## 1. MCP merges three confinement hardenings after release 2.5.0

**Date:** November 18, 2026  
**Status:** fixes merged into `v2/main`; targeted for 2.6.0, not yet in a published release  
**Practical importance:** high for agents accessing Git or the filesystem

Three fixes continue the security work published in MCP Servers 2.5.0. The Git server now refuses Windows junctions in a Git directory when they leave `--repository`, then repeats the confinement check after a command writes the working tree. The filesystem server also checks a listed directory before and after the read on Windows to detect its replacement by a junction.

**Why this matters to practitioners:** an agent may treat a repository or directory controlled by a third party as a read-only source. These cases show that an intermediate write or a Windows-specific path object could change the effective target after the initial check. Yesterday’s 2.5.0 release does not yet contain these three follow-ups.

**Possible action:** monitor and test. Keep isolating untrusted repositories, add Windows junction tests, and treat the gaps as closed in a distribution only after a release incorporates these merges.

**Primary sources:**

- Windows Git junction, PR #5628: <https://github.com/modelcontextprotocol/servers/pull/5628>
- Repeat check after a write, PR #5627: <https://github.com/modelcontextprotocol/servers/pull/5627>
- Windows listing check, PR #5622: <https://github.com/modelcontextprotocol/servers/pull/5622>

## 2. OKF changes its canonical repository and publishes project specification v0.3

**Date:** November 18, 2026  
**Status:** old repository deprecated; development moved to `open-knowledge-format/open-knowledge-format`; project specification v0.3, not a formally adopted standard  
**Practical importance:** high for agent-usable knowledge bases and business rules

The `GoogleCloudPlatform/open-knowledge-format` repository now redirects readers to the new canonical organization. The new repository publishes specification v0.3 along with bundles, a reference agent, a visualizer, and generation and consumption skills. Version 0.3 clarifies path resolution, trust-tier calculation, conformance, and `Attested Computation`. It identifies two breaking changes from v0.2: a relative path resolves from the file that contains it, and only current verification events contribute to the trust tier.

**Why this matters to practitioners:** an OKF knowledge base for weather or geospatial rules should pin its schema, preserve provenance, and prevent a migration from silently changing links or trust levels. The attestation mechanisms are especially relevant for separating an authorized rule, its parameterized execution, and verification of the result.

**Possible action:** update and test. Replace links to the old repository, declare `okf_version` explicitly, verify every relative path, and recalculate trust tiers on a copy. Treat v0.3 as the project’s current specification, not as an international standard.

**Primary sources:**

- Historical repository deprecation notice: <https://github.com/GoogleCloudPlatform/open-knowledge-format/commit/8a8ff87bfd3847c34c9ddd4fbfd9296be2aee4a3>
- New canonical repository: <https://github.com/open-knowledge-format/open-knowledge-format>
- OKF v0.3 specification: <https://github.com/open-knowledge-format/open-knowledge-format/blob/main/SPEC.md>

## 3. xarray prevents silent overflow in weighted reductions

**Date:** November 18, 2026  
**Status:** fix merged into `main`; not yet a published release  
**Practical importance:** high for quantitative aggregation

`Weighted._reduce` accumulated in the dtype of its inputs. With `uint8` or `int8` weights, or small integer data combined with Boolean weights, a sum could wrap as soon as it exceeded the dtype’s capacity. xarray now promotes Boolean and integer dtypes narrower than 64 bits to `int64` or `uint64` before the dot reduction.

**Why this matters to practitioners:** weighted means, sums, or spatial aggregations applied to weather masks and small integers could produce plausible but incorrect values without raising an exception.

**Possible action:** test. Add a case exceeding 255 or 127 to weighted-reduction tests and compare it with an explicit 64-bit accumulation; wait for an xarray release containing the fix before production.

**Primary sources:**

- xarray pull request #11868: <https://github.com/pydata/xarray/pull/11868>
- Merged commit: <https://github.com/pydata/xarray/commit/f12ea29d55a6e3a8851a9490918c43d455e201cb>

## 4. xarray fixes floating missing-value masking with NumPy 2

**Date:** November 18, 2026  
**Status:** fix merged into `main`; not yet a published release  
**Practical importance:** high for ingesting NetCDF/HDF5 and other encoded data

With NumPy 2, a fill value described at higher precision than the stored array could fail to match after conversion. For example, a `-99.9` marker in metadata could remain visible in `float32` data instead of being masked. The fix now compares the marker at the precision actually stored while preserving the original encoding metadata.

**Why this matters to practitioners:** an unmasked marker can contaminate statistics, maps, thresholds, and validation of weather cubes. It then resembles a real extreme value rather than missing data.

**Possible action:** test. Add `float16` and `float32` reads with higher-precision decimal markers under NumPy and Dask, then verify the mask before and after decoding.

**Primary sources:**

- xarray pull request #11824: <https://github.com/pydata/xarray/pull/11824>
- Merged commit: <https://github.com/pydata/xarray/commit/9764ab129d344330c87940d0761fa7c3554e521a>

## 5. GDAL fixes invalid JSON-FG output when a layer has no CRS

**Date:** November 18, 2026  
**Status:** fix merged into `master`; absent from GDAL 3.13.3  
**Practical importance:** medium to high for JSON-FG exchange

The JSON-FG writer assumed CRS84 when a layer had no declared CRS, but wrote the `coordRefSys` URI without quotes. The resulting file was not valid JSON and GDAL could not reopen it. The fix adds correct serialization and a test for this case.

**Why this matters to practitioners:** a pipeline could report a successful export while delivering a document that JSON, OGR, or OGC API clients could not consume. The defect is reproducible in GDAL 3.13.3.

**Possible action:** test. Syntax-check JSON-FG exports and perform a round trip on a layer without an explicit CRS. Wait for a GDAL release containing the fix.

**Primary sources:**

- GDAL pull request #15538: <https://github.com/OSGeo/gdal/pull/15538>
- Merged commit: <https://github.com/OSGeo/gdal/commit/6fc91d1837e811e23dbbf0676a20bdcc8e8f8a48>

## 6. OpenAI makes regional data residency configurable when creating API projects

**Date:** November 18, 2026  
**Status:** feature published for eligible organization owners  
**Practical importance:** high when privacy, regional storage, or regional processing governs an agent prototype

Eligible owners can now select a fixed region while creating an API project, or use a Global project with per-request regional selection. The documentation distinguishes regional storage from regional processing and provides a matrix by endpoint, tool, and model. Residency does not cover all system data or third-party services; some caching, tracing, and tool features also have regional limits. This option is not automatically equivalent to Zero Data Retention.

**Why this matters to practitioners:** the architecture of an agent consulting documentation, files, or geospatial APIs must check the model, storage, tools, and any MCP server separately. A regional endpoint alone does not guarantee that the whole chain stays within the same boundary.

**Possible action:** evaluate without transferring work data. Using public data, map the exact models, endpoints, and tools required; confirm contractual conditions, processing regions, and pricing before adoption.

**Primary sources:**

- November 18 release notes: <https://help.openai.com/en/articles/10128477-chatgpt-enterprise-and-edu-release-notes>
- API data-residency guide: <https://developers.openai.com/api/docs/guides/data-residency>

## 7. PARDIG and SatWeave open two global AI-weather datasets in Zarr

**Date:** November 13, 2026  
**Status:** datasets published; dated catch-up; PARDIG remains an experimental product  
**Practical importance:** high for weather AI, global observations, and cloud-native pipelines

Google DeepMind publishes PARDIG and SatWeave archives and live feeds under CC BY 4.0. PARDIG provides global precipitation estimates every 15 minutes at roughly 0.1°, with an announced average latency near five hours. SatWeave harmonizes global geostationary observations across 17 bands at 0.1°, with an hourly live feed and Zarr v3 stores. PARDIG performance results are producer evaluations and do not replace independent validation.

**Why this matters to practitioners:** both datasets enable direct testing of xarray/Zarr, spatial subsetting, object-store dissemination, and weather validation or training use cases. They do not replace official data, warnings, or validation against Canadian observations.

**Possible action:** test. Measure point/window access, transfer costs, cadence, and availability; compare PARDIG with independent references over Canada and verify SatWeave coordinate and time conventions before integration.

**Primary sources:**

- Google DeepMind announcement: <https://deepmind.google/blog/opening-the-datasets-behind-our-ai-weather-models/>
- PARDIG documentation: <https://developers.google.com/weathernext/guides/pardig>
- SatWeave documentation: <https://developers.google.com/weathernext/guides/satweave>
