Six items clear today’s publication threshold. Only one is a published release: MCP reference servers 2.4.0. The NetCDF-C fix is merged but unreleased; the GDAL/HDF5 fix remains an open pull request; the MCP file-transfer extension is explicitly experimental.

## 1. MCP reference servers 2.4.0 fixes six vulnerabilities

**Date:** November 11, 2026  
**Status:** published release with six security advisories  
**Practical importance:** high for any agent that can read files, open Git repositories, or make network requests

Version 2.4.0 publishes `@modelcontextprotocol/server-filesystem` 2.3.0 and `mcp-server-git` and `mcp-server-fetch` 2026.11.11. The most severe defect allowed configuration in an untrusted Git repository—such as `core.fsmonitor`, `diff.external`, hooks, or filters—to run a program with the server’s privileges, even through a tool described as read-only.

The other five advisories cover two race or confinement bypasses in `server-filesystem`, a Git confinement bypass through alternate object stores and linked worktrees, overly permissive IPv6 classification in Fetch’s SSRF guard, and insufficient canonicalization of paths checked against `robots.txt`. The maintainers state that the read race is narrowed rather than closed on Windows and that Windows junctions remain outside the Git fix.

**Why this matters to you:** an agent that inspects a repository, local tree, or weather API crosses three distinct trust boundaries. A “read-only” label was not sufficient to prevent code execution originating from a malicious repository.

**Possible action:** explicitly upgrade Filesystem to 2.3.0 and the Python Git/Fetch servers to 2026.11.11; verify that Git is at least version 2.31. Older date-versioned npm releases named `2025.x` or `2026.x` sort above `2.3.0`, so package managers may not offer the fixed version automatically. Keep additional isolation, especially on Windows.

**Primary sources:**

- MCP servers 2.4.0 release: <https://github.com/modelcontextprotocol/servers/releases/tag/v2.4.0>
- Repository security advisories: <https://github.com/modelcontextprotocol/servers/security/advisories>

## 2. NetCDF-C fixes two integer overflows in the classic format

**Date:** November 10, 2026  
**Status:** fix merged into `main`; no new release and no CVE announced  
**Practical importance:** high when opening untrusted NetCDF classic files

The `ncx_len_*()` macros multiplied a file-supplied element count by a fixed element size. The product could exceed `SIZE_MAX`, wrap to a small value, and result in a buffer that was too short for the later write. A second check, `check_v1hs()`, could itself accept an excessive length because the addition used to verify the end of the header overflowed.

The fix now saturates the first operation to `SIZE_MAX`, which the existing path rejects, and compares the length with the remaining space instead of performing the vulnerable addition. The file from the support ticket is now refused through the normal error path.

**Why this matters to you:** NetCDF is a common format for weather and climate data. A conversion, inspection, or catalogue service that opens externally supplied files reaches the header parser before any domain-level validation.

**Possible action:** continue isolating the decoding of untrusted files, add the malformed case to tests when the reproducer becomes available, and track the next NetCDF-C release. Do not treat current distributions as fixed until they include the commit.

**Primary sources:**

- NetCDF-C pull request #3421: <https://github.com/Unidata/netcdf-c/pull/3421>
- Merged commit: <https://github.com/Unidata/netcdf-c/commit/c43fe6975f2cbd5442abb50212fab8319773946b>

## 3. A GDAL/HDF5 fix is proposed for yesterday’s report

**Date:** November 10, 2026  
**Status:** open pull request; fix not merged, no release, and no CVE  
**Practical importance:** high for pipelines opening external HDF5 files

The proposed fix responds to GDAL report #15494 covered in the November 10 edition. It now checks the return value of `H5Aread()`; on failure, GDAL emits a warning and no longer interprets uninitialized pointers as strings. Variable-length HDF5 memory is reclaimed only after a successful read.

**Why this matters to you:** the reported path concerns dataset opening and metadata, so an HDF5/NetCDF pipeline can reach it before a raster subset or application-level validation.

**Possible action:** track the pull-request review and tests. For early validation, build the commit in an isolated image and replay the minimized file; do not deploy an unmerged fix without local assessment.

**Primary sources:**

- GDAL pull request #15500: <https://github.com/OSGeo/gdal/pull/15500>
- Original GDAL report #15494: <https://github.com/OSGeo/gdal/issues/15494>

## 4. MCP publishes an experimental draft for transferring files outside model context

**Date:** November 10, 2026, made public in the main repository on November 11  
**Status:** experimental, unapproved extension with no reference implementation  
**Practical importance:** high over the medium term for agents handling large weather or geospatial files

The proposed `io.modelcontextprotocol/files` extension lets a tool mark an argument with `x-mcp-file`. Small files may be sent inline as base64, while large files travel directly by HTTPS to a server-provided target without putting their bytes or URL in model context. Uploads use an `upload_required` result and `requestState`; downloads are currently described in `_meta`.

The draft also defines size, MIME-type, and digest rules, plus `credentials: omit|include`. It requires clients to reject redirects and target-supplied `Authorization` headers. One security question remains open: user approval happens before the exact destination is known, and mandatory origin allowlisting for `omit` transfers has not yet been decided.

**Why this matters to you:** GRIB2, NetCDF, Zarr, GeoParquet, and large CSV files are poor fits for transport inside JSON-RPC or an LLM context. This proposal separates the agent decision, machine-actionable metadata, and byte transfer.

**Possible action:** track the work and prototype only with public or synthetic data. Locally require a destination allowlist, verify size and digest, scan downloaded files as untrusted, and transfer no work data without explicit authorization. Do not build a production contract on the current draft.

**Primary sources:**

- MCP announcement: <https://blog.modelcontextprotocol.io/posts/exploring-file-uploads-and-downloads-in-mcp/>
- Extension draft: <https://github.com/modelcontextprotocol/experimental-ext-file-uploads/blob/main/specification/draft/file-uploads.md>

## 5. GDAL’s GeoParquet validator incorrectly rejects some `Point Z` data

**Date:** November 10, 2026  
**Status:** open report; no merged fix  
**Practical importance:** medium for 3D GeoParquet conformance checks

The internal `validate_geoparquet` lookup currently maps `ogr.wkbPoint25D` to `Point` rather than `Point Z`. A file correctly written by GDAL with `geometry_types: ["Point Z"]` can therefore be declared invalid by GDAL’s own validator. The reporter reproduces the result with GDAL 3.13.1 and a 3.14 development build.

**Why this matters to you:** an automated check can block publication of valid 3D GeoParquet or trigger unnecessary changes to the data. The report concerns the validator, not evidence that the written file is corrupt.

**Possible action:** distinguish this false negative from a true conformance failure, retain a `Point Z` test, and track the upstream correction before making this check blocking.

**Primary source:**

- GDAL issue #15498: <https://github.com/OSGeo/gdal/issues/15498>

## 6. Gemini 4 Carbon becomes available through the Gemini API

**Date:** November 10, 2026  
**Status:** model released on the paid tier; `/swarm` remains a preview in Google Antigravity  
**Practical importance:** medium for evaluating complex documentary and scientific agents

Google has made Gemini 4 Carbon available in Google AI Studio and Gemini for business at an announced introductory price of US$2 per million input tokens and US$10 per million output tokens. The model targets long-horizon agentic workflows, scientific reasoning, coding, and analysis of complex documents. Google says it uses more tokens than Gemini 4 Argon to extend reasoning and verification loops.

Availability and pricing are verifiable facts; the quality, safety, and per-task cost gains rely mainly on evaluations and partners presented by Google and do not independently validate weather workflows.

**Why this matters to you:** this profile may suit an evaluation that transforms public API documentation, published rules, and geospatial metadata into structured outputs, provided facts and tool calls remain deterministically validated.

**Possible action:** test only with public or authorized sources using a fixed evaluation set. Measure factual accuracy, schema compliance, total cost, latency, and source attribution; do not assume work data may be transferred to the service.

**Primary source:**

- Google announcement: <https://blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-4-carbon-now-available/>

No sufficiently significant new change was confirmed today for GeoMet/ECCC, WIS2, OGC, MapServer, PROJ/pyproj, pygeoapi, xarray/Dask, kerchunk, or OKF.
