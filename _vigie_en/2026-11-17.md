Six recent changes clear the publication threshold. The OGC standard dated November 12 is included as a clearly dated catch-up; the five code fixes were merged after the previous edition. None of those fixes is included in a published release yet.

## 1. OGC API — Common Part 2: Geospatial Data becomes a 1.0 standard

**Date:** November 12, 2026  
**Status:** OGC 1.0 standard published; approval dated October 15, 2026  
**Practical importance:** high for OGC API architecture and collection reuse

OGC API — Common Part 2 formalizes the common elements used by a Web API to list and describe its collections of geospatial data. It provides a shared foundation that specialized OGC API standards can reuse instead of redefining collection discovery and description independently.

**Why this matters to practitioners:** a GeoMet or pygeoapi implementation exposing multiple data families benefits from aligning collection metadata and conformance declarations with this common foundation. It reduces divergence between OGC API — Features, Coverages, EDR, and other APIs, and helps generic clients or agent tools discover resources deterministically.

**Possible action:** evaluate. Compare existing `collections` responses and conformance declarations with Part 2 requirements before changing an API; treat the document as an adopted standard, not a proposal.

**Primary source:**

- OGC API — Common — Part 2: Geospatial Data 1.0 standard: <https://docs.ogc.org/is/20-024/20-024.html>

## 2. GDAL fixes ignored resampling during a resized Warped VRT read

**Date:** November 16, 2026  
**Status:** fix merged into `master`; absent from the currently published GDAL 3.13.3 release  
**Practical importance:** high for raster reprojection and resizing pipelines

The optimized `VRTWarpedDataset::IRasterIO()` path used the warp resampling and could ignore the algorithm requested when reading a complete image into a differently sized buffer. A pipeline with `reproject` followed by `resize -r average` could therefore produce a nearest-neighbour result. The fix now reserves that shortcut for nearest-neighbour.

**Why this matters to practitioners:** resampling choice directly changes values in weather grids, accumulations, and continuous indices. In the project’s test case, 0/200 stripes remain at 0/200 before the fix, while the expected aggregation produces values around 88 to 111.

**Possible action:** test and monitor. Add a numerical test comparing a reprojection+resize pipeline with two separate operations for `average`, `bilinear`, or the algorithm actually used; wait for a GDAL release containing the fix before production.

**Primary sources:**

- GDAL pull request #15427: <https://github.com/OSGeo/gdal/pull/15427>
- Merged commit: <https://github.com/OSGeo/gdal/commit/aeb88659f230e86bde92fa6519dcb92bb0e4ba08>
- GDAL releases: <https://github.com/OSGeo/gdal/releases>

## 3. GDAL avoids a pixel shift in some multithreaded GeoTIFF reads

**Date:** November 16, 2026  
**Status:** fix merged into `master`; absent from the currently published GDAL 3.13.3 release  
**Practical importance:** high for mosaics and fractional-window reads

With a window expressed in floating-point pixel coordinates and `GDAL_NUM_THREADS` greater than 1, the multithreaded GeoTIFF path could ignore the fractional window and use truncated integer coordinates. The report reproduces a one-column difference — 800 with one thread versus 799 with two — and describes Copernicus mosaic chunks shifted by one pixel without an error. GDAL now disables that multithreaded path for these windows and emits a warning.

**Why this matters to practitioners:** converting a bbox to a pixel window often produces tiny floating-point errors, especially for geographic resolutions such as 1/3600°. A parallel process could therefore be fast but spatially inconsistent with the same single-threaded process.

**Possible action:** test. Repeat bbox-derived window reads with one and several threads and compare edge pixels; monitor the warning added by GDAL and wait for a release containing the fix.

**Primary sources:**

- GDAL issue #15513: <https://github.com/OSGeo/gdal/issues/15513>
- GDAL pull request #15529: <https://github.com/OSGeo/gdal/pull/15529>
- Merged commit: <https://github.com/OSGeo/gdal/commit/f6983b320bf6fc3758f71d49bbd4fe968c5ff7cc>

## 4. Zarr fixes Numcodecs filter decoding order after a transpose

**Date:** November 16, 2026  
**Status:** fix merged into `main`; absent from the currently published Zarr-Python 3.4.2 release  
**Practical importance:** high for array integrity when using filters with `TransposeCodec`

Arrays combining a Numcodecs `Delta` or `FixedScaleOffset` filter with `TransposeCodec` could be decoded in memory order rather than logical order, then read back with scrambled values. The fix makes the buffer C-contiguous before decoding and extends round-trip tests to include a transpose.

**Why this matters to practitioners:** this is a value-fidelity problem, not merely a performance or metadata issue. A seemingly valid codec chain could write and then read a different array, which is especially concerning for quantitative grids.

**Possible action:** test. Add an exact round-trip using the filters and transpose order present in the datasets; wait for the next Zarr-Python release before considering the problem fixed in a published environment.

**Primary sources:**

- Zarr-Python pull request #4558: <https://github.com/zarr-developers/zarr-python/pull/4558>
- Merged commit: <https://github.com/zarr-developers/zarr-python/commit/d4d4d38b300204236014d0b2fb78b8aa8123dea9>
- Zarr-Python releases: <https://github.com/zarr-developers/zarr-python/releases>

## 5. pyproj fixes `sync --system-directory` so grids reach the correct directory

**Date:** November 16, 2026  
**Status:** fix merged into `main`; absent from the currently published pyproj 3.8.0 release  
**Practical importance:** medium to high for transformations that depend on PROJ grids

`pyproj sync --system-directory` separated directories with `os.path.sep` instead of `os.pathsep`. On Linux, the target became empty; on Windows, it could become only the drive letter. Grids and `files.geojson` were consequently placed in the current directory rather than the first PROJ data directory.

**Why this matters to practitioners:** the command could appear to succeed while PROJ subsequently failed to find the grid required for a precise transformation. This directly affects environment reproducibility and can cause a less accurate fallback operation to be selected or a transformation to fail.

**Possible action:** verify. Check the actual file location after `pyproj sync --system-directory` and test a transformation that explicitly depends on the grid; use a validated `--target-directory` as a local measure if needed, then wait for a pyproj release with the fix.

**Primary sources:**

- pyproj issue #1672: <https://github.com/pyproj4/pyproj/issues/1672>
- pyproj pull request #1673: <https://github.com/pyproj4/pyproj/pull/1673>
- Merged commit: <https://github.com/pyproj4/pyproj/commit/97e7de0ad0c8d0d804d714a26bf1cb654a7c1d6b>

## 6. Zarr fixes v2→v3 migration for Blosc `AUTOSHUFFLE` arrays

**Date:** November 16, 2026  
**Status:** fix merged into `main`; absent from the currently published Zarr-Python 3.4.2 release  
**Practical importance:** medium for migrations of historical Zarr stores

`zarr migrate v3` failed on a Zarr v2 array using `Blosc.AUTOSHUFFLE`, because Numcodecs serializes that option as `shuffle: -1` while the v3 converter accepted only 0 through 2. Migration now maps the value to `bitshuffle` for one-byte items and `shuffle` for larger items, matching Numcodecs behavior.

**Why this matters to practitioners:** fully readable v2 stores could be impossible to migrate automatically. The fix also preserves the shuffle mode actually used, avoiding a silent encoding change when new chunks are rewritten.

**Possible action:** test. Inventory v2 metadata containing `shuffle: -1`, migrate a copy, and compare data, metadata, and Blosc headers before any in-place migration; wait for a Zarr-Python release containing the fix.

**Primary sources:**

- Zarr-Python pull request #4630: <https://github.com/zarr-developers/zarr-python/pull/4630>
- Merged commit: <https://github.com/zarr-developers/zarr-python/commit/13f75f7774861ad94ad83b6d4aa2e14e9eb78150>
