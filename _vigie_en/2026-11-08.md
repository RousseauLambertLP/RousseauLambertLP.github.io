## 1. MCP rewrites its authorization guide and hardens the v2 SDK examples

**Date:** November 8, 2026  
**Status:** guide and examples merged for the 2026-07-28 revision and the draft; no new normative protocol release  
**Practical importance:** medium to high for remote HTTP MCP servers providing access to protected APIs or data

The MCP authorization guide now presents **Client ID Metadata Documents** as the main client-registration path and marks **Dynamic Client Registration (DCR)** as deprecated. The former provider-specific walkthrough has been replaced with provider-agnostic requirements and TypeScript, Python, and C# examples using the v2 SDKs.

The revision adds or makes explicit several checks: matching the `audience` to the MCP resource, exact validation of the `issuer` and `iss` parameter, scope verification, `Host` and `Origin` header controls, a small clock-skew allowance, limits on key downloads, opaque-token handling, and behaviour behind a proxy. It also reiterates that this OAuth flow targets HTTP transports; a local stdio server normally uses credentials supplied through its environment.

**Why this matters to you:** an agent accessing weather or geospatial APIs through MCP introduces an authorization boundary in front of potentially sensitive data and tools. A valid JWT signature is not enough when the token targets another resource, comes from another issuer, or has inadequate scopes. Origin and host controls also matter when the server sits behind a reverse proxy.

**Possible action:** compare any remote HTTP MCP implementation against the new checklist; test at least incorrect `aud`/`iss`, insufficient scopes, rejected `Host`/`Origin` headers, JWKS or introspection outages, and deployments behind a proxy. Treat this revision as improved implementation guidance, not as a required protocol migration.
