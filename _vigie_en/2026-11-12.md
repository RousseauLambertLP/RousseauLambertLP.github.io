Seven changes clear today’s publication threshold. All software fixes below are merged but absent from current stable releases; the MCP announcement describes a work calendar and is not a new protocol version.

## 1. GDAL fixes an HDF-EOS buffer overflow

**Date:** reported November 6; fix merged November 12, 2026  
**Status:** fix merged into `master`; no release or CVE announced  
**Practical importance:** high when opening external HDF-EOS/HDF4 files

`SWgetfillvalue()` and `GDgetfillvalue()` built an attribute name in an 80-character buffer with `strcat()`. A sufficiently long `DataFieldName` supplied through file metadata could overflow the stack while the file was being opened. The reporter reproduced the defect with a valid HDF-EOS2 file and `gdalinfo`, on GDAL 3.8.4 and a 3.14 development build. The fix replaces the concatenations and increases the buffer to match upstream code.

**Why this matters to you:** HDF4/HDF-EOS can enter scientific conversion or cataloguing pipelines. The defect is reached during opening, before domain validation or a raster extraction can protect the process.

**Possible action:** continue isolating untrusted files and add the reproducer to ingestion tests. Track the next GDAL release; current stable installations do not yet include the commit.

**Primary sources:**

- GDAL issue #15486: <https://github.com/OSGeo/gdal/issues/15486>
- Merged pull request #15497: <https://github.com/OSGeo/gdal/pull/15497>
- Merged commit: <https://github.com/OSGeo/gdal/commit/687ad8d5c122c63982deea735486e42f3ac8682e>

## 2. The GDAL/HDF5 fix tracked yesterday is now merged

**Date:** November 12, 2026  
**Status:** fix merged into `master`; no release or CVE announced  
**Practical importance:** high for pipelines opening external HDF5 files

GDAL now checks for failure from `H5Aread()` before concatenating or reclaiming variable-length HDF5 strings. This closes the path in which an uninitialized pointer could be interpreted after an attribute read failure. The pull request was still open in the November 11 edition.

**Why this matters to you:** HDF5 and NetCDF metadata are read very early in weather and climate pipelines. The change reduces a crash or invalid-memory-read risk on unusual or untrusted inputs.

**Possible action:** replay the minimized file in an image built from the commit, then wait for a release before considering distributed environments fixed.

**Primary sources:**

- GDAL pull request #15500: <https://github.com/OSGeo/gdal/pull/15500>
- Merged commit: <https://github.com/OSGeo/gdal/commit/bd20a68c30446ac800b7bfdbee3857571e3aee02>

## 3. GDAL fixes the GeoParquet `Point Z` false negative

**Date:** November 12, 2026  
**Status:** fix merged into `master`; not yet released  
**Practical importance:** medium for 3D GeoParquet validation

The validator now correctly maps `ogr.wkbPoint25D` to `Point Z`. A file written by GDAL with `geometry_types: ["Point Z"]` should therefore no longer be rejected by GDAL’s own validator. The defect was still open in the previous edition.

**Why this matters to you:** CI checks can distinguish a real conformance failure from a validator false negative without unnecessarily blocking publication of valid 3D GeoParquet.

**Possible action:** keep an end-to-end write → validate test for `Point Z`, and remove any temporary exception only after adopting a release that contains the fix.

**Primary sources:**

- GDAL pull request #15517: <https://github.com/OSGeo/gdal/pull/15517>
- Merged commit: <https://github.com/OSGeo/gdal/commit/7b845fc3216ccac920940642352b97ef26a18410>

## 4. OGR aligns GeoPackage spatial filtering between Arrow and the classic API

**Date:** November 12, 2026  
**Status:** fix merged into `master`; not yet released  
**Practical importance:** medium for GeoPackage-to-Arrow pipelines

With a spatial filter covering a layer’s full extent, `GetArrowStream()` could retain features whose geometry was `NULL`, while `GetNextFeature()` excluded them as required by the OGR contract. The path using a smaller filter and the R-tree index did not have this divergence. The fix now skips null geometries whenever a spatial filter is active.

**Why this matters to you:** two read paths over the same layer could produce different feature counts, weakening tests, statistics, and cloud-native conversions built on Arrow.

**Possible action:** add a comparison test between Arrow and the classic API with `NULL` and `EMPTY` geometries, using both a full-extent filter and a smaller filter.

**Primary sources:**

- GDAL pull request #15470: <https://github.com/OSGeo/gdal/pull/15470>
- Merged commit: <https://github.com/OSGeo/gdal/commit/c5d794fe0c8feae8bf5ab9c19094b3826e5d458f>

## 5. PROJ corrects the decimetre-to-metre conversion

**Date:** November 11, 2026  
**Status:** fix merged into `master`; not yet released  
**Practical importance:** medium when a CRS or operation explicitly uses decimetres

The PROJ database declared `1 dm = 0.01 m` instead of `0.1 m`, an error by a factor of ten. According to the pull request, this value had been present for at least six years. The fix updates the generated database and related tests.

**Why this matters to you:** ordinary transformations in metres or degrees do not change, but any CRS or parameter expressed in decimetres could have been scaled incorrectly. pyproj inherits this PROJ database.

**Possible action:** search the CRS and operations actually used for the `decimetre`/`decimeter` unit. If it appears, compare results before and after the commit; otherwise no immediate action is needed.

**Primary sources:**

- PROJ pull request #4943: <https://github.com/OSGeo/PROJ/pull/4943>
- Merged commit: <https://github.com/OSGeo/PROJ/commit/890f8a0599ee4600344c8b630df5e4bc4762c83f>

## 6. MCP adopts a predictable two-release-per-year cycle

**Date:** November 11, 2026  
**Status:** official calendar; no new normative version  
**Practical importance:** medium for planning implementations and interoperability tests

MCP now plans a specification release every six months, generally on the last Tuesday of March and September. The next target is March 30, 2027, with the planned identifier `2027-03-30`; proposal deadlines and SDK beta dates are to be published beforehand.

**Why this matters to you:** a known calendar makes it possible to align MCP servers exposing weather/geospatial APIs, compatibility tests, and security reviews with explicit milestones instead of continuously changing targets that are difficult to freeze.

**Possible action:** track proposal windows and plan protocol/SDK validation ahead of March 2027. This announcement alone requires no production change.

**Primary sources:**

- MCP announcement: <https://blog.modelcontextprotocol.io/posts/mcp-release-cycle/>
- Publication pull request #3541: <https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3541>

## 7. `zarr-metadata` changes the values derived by `create_default()`

**Date:** November 12, 2026  
**Status:** breaking change merged in the subproject; no release published  
**Practical importance:** medium for Zarr metadata generators and validators

`create_default()` now derives the fill value, array-to-bytes codec, and some chunk values from the supplied type and shape. For example, Zarr V3 strings receive `vlen-utf8`, bytes receive `vlen-bytes`, time types receive `NaT`, and a zero-length dimension receives a chunk length of 1 in V2. Some documents that previously failed can now be created, while serialized default values change.

**Why this matters to you:** an agent or catalogue generating machine-actionable metadata may emit a different document without changing its call. This affects byte-for-byte tests, fill-value assumptions, and interoperability of variable-size types.

**Possible action:** pin `zarr-metadata`, test every weather dtype in use, and compare generated JSON documents before and after the change. Wait for a release and review its changelog before upgrading.

**Primary sources:**

- zarr-python pull request #4621: <https://github.com/zarr-developers/zarr-python/pull/4621>
- Merged commit: <https://github.com/zarr-developers/zarr-python/commit/923498db4175f9a3d8dcca8b0e416d1193e267cf>

No sufficiently significant new change was confirmed today for GeoMet/ECCC, WIS2, OGC, MapServer, pygeoapi, xarray/Dask, kerchunk, OKF, or weather AI models.
