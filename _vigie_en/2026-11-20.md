Four recent changes cross the practical-relevance threshold today. The netCDF-C and xarray fixes are **merged into the main codebase but not yet included in a release**. For MCP Events, the SEP is final while publication of the normative Beta specification is still in progress.

## 1. netCDF-C now bounds DAP4 chunk counts

**Date:** November 19, 2026  
**Importance:** high  
**Status:** fix merged into `main`; no published release includes it yet, and no CVE has been confirmed for this issue.

**Summary:** netCDF-C now validates the 24-bit count declared in a DAP4 chunk header against the response's actual size. Without this bound, a truncated or crafted DAP4 response could cause out-of-bounds reads in `NCD4_dechunk` during `nc_open`.

**Why this matters to your work:** scientific clients opening remote `dap4://` resources — or untrusted local `.dap` files — should not consider the issue fixed until a release containing the commit is deployed. The surface directly affects remote access to NetCDF data.

**Possible action:** inventory DAP4 use, restrict untrusted endpoints, and test truncated responses in an isolated environment. If an immediate fix is required, assess a controlled backport of the commit rather than assuming netCDF-C 4.10.1 is protected.

**Primary sources:** [netCDF-C commit](https://github.com/Unidata/netcdf-c/commit/69d79a91d4f60f5ffc3eb365c6859a1c8a4ca7bd), [PR #3481](https://github.com/Unidata/netcdf-c/pull/3481), [issue #3467](https://github.com/Unidata/netcdf-c/issues/3467), [netCDF-C releases](https://github.com/Unidata/netcdf-c/releases)

## 2. xarray now rejects time encodings that produced only `NaT` or `inf`

**Date:** November 19, 2026  
**Importance:** high  
**Status:** change merged into `main`; not yet included in an xarray release.

**Summary:** when `datetime64[s]` or `timedelta64[s]` data was forced to finer units such as milliseconds, microseconds, or nanoseconds, xarray could silently encode every value as `NaT` for integer output or `inf` for floating-point output. The code now raises an explicit `ValueError`.

**Why this matters to your work:** an incompatible CF/NetCDF encoding setting could silently destroy an entire time coordinate, including forecast reference or valid times. The explicit failure makes the problem detectable before dissemination.

**Possible action:** add round-trip tests for second-resolution arrays forced to use finer units, and explicitly select units compatible with the data resolution.

**Primary sources:** [xarray commit](https://github.com/pydata/xarray/commit/adcd4e9821d64cdfea9a43f263d1f273075cad33), [PR #11907](https://github.com/pydata/xarray/pull/11907), [xarray releases](https://github.com/pydata/xarray/releases)

## 3. MCP Events: final SEP, Beta registration, normative specification still pending

**Date:** November 19–20, 2026  
**Importance:** medium to high  
**Status:** SEP-3415 is final; the extension is registered as Beta in the documentation; the normative publication PR remained pending in the verified canonical repository. This is not a stable MCP Core feature.

**Summary:** the `io.modelcontextprotocol/events` extension defines discovery of typed events and three delivery modes — polling, streaming, and webhooks — with opaque cursors, optional replay, and gap indication. The documentation registers it as Beta, but the PR adding the Beta specification to the `ext-events` repository had not yet merged when checked.

**Why this matters to your work:** the extension could replace custom polling and webhook mechanisms used to trigger agents when weather data is published, APIs change, or incidents occur. Payloads remain untrusted; authorization, signatures, SSRF prevention, replay, and gap handling still need explicit design.

**Possible action:** monitor and prototype only. Do not base a production service on the incomplete Beta; require typed schemas, signed callbacks, and tests for cursors, replay, and gaps.

**Primary sources:** [SEP-3415](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/3415-events-extension.md), [final SEP commit](https://github.com/modelcontextprotocol/modelcontextprotocol/commit/8a18b4b3292b9f9b3aee73f6325f9f62f19a89f9), [documentation PR #3568](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3568), [normative `ext-events` PR #24](https://github.com/modelcontextprotocol/ext-events/pull/24)

## 4. netCDF-C fixes a stray `_Netcdf4Dimid` attribute

**Date:** November 19, 2026  
**Importance:** medium  
**Status:** fix merged into `main`; not yet included in a netCDF-C release.

**Summary:** a regular HDF5 dataset that was not a dimension scale could incorrectly receive the internal `_Netcdf4Dimid` attribute when dimensions and variables shared certain names. The fix now prevents this inconsistent metadata.

**Why this matters to your work:** tools that inspect dimension scales or convert NetCDF-4/HDF5 files may misinterpret a regular variable. The case is conditional, but it affects metadata interoperability and fidelity.

**Possible action:** add a regression test with dimension/variable name collisions, especially in parallel NetCDF-4 pipelines, then wait for an official release before removing any workarounds.

**Primary sources:** [netCDF-C commit](https://github.com/Unidata/netcdf-c/commit/39a86a6e84af94697fba9a06006c899bc9d9f9ea), [PR #3483](https://github.com/Unidata/netcdf-c/pull/3483), [issue #2477](https://github.com/Unidata/netcdf-c/issues/2477)
