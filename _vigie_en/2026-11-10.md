Five changes clear today’s publication threshold. The two GDAL items are open reports with no CVE or published fix; the three Zarr items are merged changes that are not yet present in a stable release.

## 1. GDAL: uninitialized-pointer read reported in the HDF5 driver

**Date:** November 9, 2026  
**Status:** open issue and sanitizer reproduction; defect not yet confirmed or fixed by maintainers  
**Practical importance:** high when opening untrusted HDF5 files

The report states that `HDF5AttrIterate()` does not check for failure from `H5Aread()` when reading a variable-length string attribute. After that failure, GDAL can interpret an uninitialized pointer as a string. The reporter reproduces an invalid read while opening the dataset with GDAL 3.13.3, AddressSanitizer, and UndefinedBehaviorSanitizer; no separate raster read is required.

This is not a CVE, a published security advisory, or evidence of remote exploitation. The minimized file has been made available in the issue so maintainers can verify it.

**Why this matters to you:** HDF5 and NetCDF can enter weather-data conversion or dissemination pipelines. If a service opens third-party files in the API process, a metadata-stage memory defect deserves treatment as a trust-boundary concern.

**Possible action:** track the issue and test the reproducer in an isolated image using the actually deployed version. Keep process isolation and resource limits for untrusted inputs; do not present the issue as confirmed across all versions before upstream analysis.

**Primary source:**

- GDAL issue #15494: <https://github.com/OSGeo/gdal/issues/15494>

## 2. Zarr-Python adds partial decoding for uncompressed chunks

**Date:** November 9, 2026  
**Status:** feature merged into `main`; no new release published  
**Practical importance:** high for remote access and large virtual chunks

When `BytesCodec` is the only codec, Zarr-Python can now read only the byte ranges corresponding to requested rows instead of fetching the complete chunk. Selections touching every row and chunks using any other codec continue to be read in full.

In the author’s example, transferred data fell from 20 MB to 2 KB when reading 100 samples from a single uncompressed 20 MB chunk. This illustrates the potential but is not an independent benchmark for every store.

**Why this matters to you:** weather cubes virtualized from HDF5 or other files can expose very large chunks. A small spatial, temporal, or vertical extraction should not necessarily trigger transfer of the full chunk from remote object storage.

**Possible action:** measure HTTP requests and transferred bytes on a representative store, with and without compression, then verify values and dimension ordering. Wait for a Zarr-Python release before basing a performance guarantee on this optimization.

**Primary sources:**

- zarr-python pull request #4458: <https://github.com/zarr-developers/zarr-python/pull/4458>
- Merged commit: <https://github.com/zarr-developers/zarr-python/commit/90faa99d2ab9722599c0ab1fbd4d721bc5030df6>

## 3. GDAL/GeoParquet: crash reported with read-only Arrow buffers

**Date:** report opened November 8 and clarified November 10, 2026  
**Status:** open discussion; no CVE, merged fix, or upstream advisory  
**Practical importance:** medium to high for Arrow-to-GeoParquet pipelines

A report says that writing some polygons to GeoParquet can modify the input WKB while normalizing ring orientation. If the Arrow buffers come from a read-only memory-mapped IPC file, this modification can cause a `SIGSEGV`. The reported case concerns GDAL 3.13.3 and a 3.14 development build.

The upstream discussion notes that `WriteArrowBatch()` may take ownership of the array and that the Parquet driver normalizes orientation by default. The reporter confirmed that `POLYGON_ORIENTATION=UNMODIFIED` avoids the crash in their tests, but this setting changes the output contract: it is a workaround to validate, not a fix.

**Why this matters to you:** Arrow and GeoParquet are central to cloud-native geospatial pipelines. A pipeline transforming memory-mapped batches can meet the reported conditions even when its geometries are valid.

**Possible action:** add a test with read-only Arrow buffers and polygons that require reorientation. Evaluate `POLYGON_ORIENTATION=UNMODIFIED` only when non-normalized orientation is acceptable to consumers; track the maintainers’ decision.

**Primary source:**

- GDAL issue #15491: <https://github.com/OSGeo/gdal/issues/15491>

## 4. Zarr-Python deprecates seven ignored version-2 parameters

**Date:** November 9, 2026  
**Status:** deprecation merged into `main`; removal announced after February 2027; no release published  
**Practical importance:** medium for Zarr-Python 2-to-3 migrations

The `synchronizer`, `chunk_store`, `cache_metadata`, `cache_attrs`, `object_codec`, `read_only`, and `meta_array` parameters, still accepted by several Zarr-Python 3 APIs, had no effect. They will now produce a `ZarrDeprecationWarning` and will be removed in a release after February 2027.

The `read_only` case is especially misleading: its presence in a Zarr-Python 3 call did not actually protect the array from modification.

**Why this matters to you:** an xarray/Zarr pipeline may have retained these parameters during migration and incorrectly assume that locking, caching, or separate chunk storage is active.

**Possible action:** search the codebase for all seven arguments and turn deprecation warnings into CI failures. Replace each use with a supported capability rather than silently removing a security or performance assumption.

**Primary sources:**

- zarr-python pull request #4522: <https://github.com/zarr-developers/zarr-python/pull/4522>
- Merged commit: <https://github.com/zarr-developers/zarr-python/commit/98aff7b103c7ccc71d536a6dd0a26bd42940c192>

## 5. `zarr-metadata` introduces `JSONWriter` and changes its writing API

**Date:** November 9, 2026  
**Status:** breaking change merged into the `zarr-metadata` subproject; no release published  
**Practical importance:** medium for tools that directly produce or validate Zarr metadata

The `to_key_value()` method now receives a `JSONWriter` or a settings mapping instead of the named `indent` argument. For example, `to_key_value(indent=2)` becomes `to_key_value({"indent": 2})`. The writer also centralizes key sorting, ASCII escaping, and trailing-newline handling, and rejects ambiguous settings or settings that could produce invalid JSON.

This change affects the new `zarr-metadata` subproject, not the general `zarr` array-writing API.

**Why this matters to you:** a validator, catalogue, or agent that directly serializes machine-actionable metadata needs deterministic, conformant bytes. The new abstraction is useful, but it breaks calls built on the former `indent` parameter.

**Possible action:** if `zarr-metadata` is being evaluated in a prototype, pin its version and add byte-for-byte tests for `zarr.json`; migrate to the settings mapping or `JSONWriter` only when adopting the corresponding release.

**Primary sources:**

- zarr-python pull request #4610: <https://github.com/zarr-developers/zarr-python/pull/4610>
- Merged commit: <https://github.com/zarr-developers/zarr-python/commit/ee1b44c70ccd8ba027e17dbeee580fb255dd8745>
