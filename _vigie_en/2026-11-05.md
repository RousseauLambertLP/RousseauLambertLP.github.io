## 1. MCP official servers 2.3.0 adds concrete access guardrails

**Date:** November 4, 2026  
**Status:** published release  
**Practical importance:** high

Release 2.3.0 groups several updates. Filesystem server 2.2.0 notably adds `--read-only` and `--confine-roots`, new copy and append tools, and file resources. Fetch server 2026.11.4 adds an allowed-host list, a configurable timeout, and HTML extraction in a bounded subprocess. Filesystem also upgrades `minimatch` to a version patched for denial-of-service vulnerability CVE-2026-118764.

**Why it matters to you:** these options directly reduce the reach of tools used by agents to consult documentation, configurations, or APIs. For a weather or geospatial knowledge service, read-only operation restricted to precise roots and an explicit host list is a useful defence against excessive access and prompt-injection effects. These application guardrails do not, however, replace operating-system or container isolation.

**Possible action:** update the affected servers, enable `--read-only` and `--confine-roots` when writes are unnecessary, restrict `--allowed-hosts`, and then test expected flows and denials.

**Sources:**

- MCP official servers v2.3.0: <https://github.com/modelcontextprotocol/servers/releases/tag/v2.3.0>
- `minimatch` advisory GHSA-g3hv-75wg-m249 / CVE-2026-118764: <https://github.com/isaacs/minimatch/security/advisories/GHSA-g3hv-75wg-m249>
- Filesystem server documentation: <https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem>

## 2. pygeoapi now uses the collection extent for a map request without `bbox`

**Date:** November 5, 2026  
**Status:** code merged into `master`, not yet a published release  
**Practical importance:** high

The change merged in PR #2475 replaces the global default extent in `get_collection_map()` with the collection’s configured `extents.spatial.bbox` and CRS. A request that explicitly supplies `bbox` keeps its parameter-driven behaviour.

**Why it matters to you:** an OGC API — Maps request without `bbox` will now produce a map focused on the collection’s actual extent rather than a global view. This is usually more useful, but it can change rendering, generation cost, cache keys, and contract tests. For weather collections exposed through APIs, the accuracy of the spatial extent and its CRS becomes even more important.

**Possible action:** verify collection `extents.spatial`, then add a no-`bbox` request test before adopting a future pygeoapi release that contains this change.

**Sources:**

- pygeoapi PR #2475: <https://github.com/geopython/pygeoapi/pull/2475>
- Merged commit: <https://github.com/geopython/pygeoapi/commit/3e38a89aa12faab7099be660b99575c9cf111a0c>

## 3. PROJ extends 2D/3D conversions to `EngineeringCRS`

**Date:** November 5, 2026  
**Status:** code merged, not yet a published release  
**Practical importance:** medium to low for operational weather services

PR #4926 adds `promoteTo3D` and `demoteTo2D` support for `EngineeringCRS`, with associated tests. This CRS type is primarily used for local or engineering reference frames; it does not replace the geographic and projected CRS commonly used by weather products.

**Why it matters to you:** the change improves consistency for pipelines that must move a local reference frame between two and three dimensions, for example for facilities, instruments, or local frames. Its immediate impact is limited when services use only standard geographic or projected CRS.

**Possible action:** monitor the next PROJ release; if `EngineeringCRS` is used, prepare a 2D → 3D → 2D WKT/PROJJSON round-trip test.

**Sources:**

- PROJ PR #4926: <https://github.com/OSGeo/PROJ/pull/4926>
- Merged commit: <https://github.com/OSGeo/PROJ/commit/be0df1e07a3ce21f3aafc29607b0a3295f588137>
