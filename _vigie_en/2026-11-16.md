Two code changes merged since the previous edition clear the publication threshold. The main one directly concerns WIS2 data acquisition. Neither is a published release yet.

## 1. WIS2 Downloader prepares beta 1.0.0b2 with stronger resilience and supply chain

**Date:** November 16, 2026  
**Status:** pull request merged into the official repository; the `v1.0.0b2` tag and release were not published when checked  
**Practical importance:** high for operational WIS2 data acquisition

The official WMO repository merged a broad set titled “Final changes for release.” It notably fixes lost subscriptions after an MQTT reconnection, allows a broker to be preferred by delaying queueing, preserves subscription information across restarts, and accepts `rel=update` notifications when their `pubtime` is newer instead of discarding them as duplicates. Retention no longer scans every file: downloads are organized by day and old daily directories are removed as units.

The same set removes plaintext credentials from logs and prepares a release pipeline that produces scanned multi-architecture images pinned by digest, with SBOMs and provenance attestations. These capabilities are in the merged code, but should not be described as an installable version until the tag and release artifacts exist.

**Why this matters to practitioners:** reconnection, cross-broker deduplication, and correct update handling determine whether a WIS2 collector continues receiving data after an outage and retains the latest version of a product. The new retention strategy also targets volumes of several million files, relevant to continuous weather-data ingestion.

**Possible action:** test and monitor. On an isolated instance, simulate a broker outage and reconnection, two copies of the same notification, and a `rel=update` notification; also verify date-based retention. For a stable deployment, wait for the `v1.0.0b2` tag, attested images, and published artifacts.

## 2. xarray uses Zarr’s public asynchronous API with a compatible fallback

**Date:** November 15, 2026  
**Status:** change merged into xarray’s main branch; not a published release  
**Practical importance:** medium for xarray–Zarr compatibility and asynchronous reads

xarray now accesses `zarr.Array.async_array`, a public API since Zarr 3.1.4, while retaining a fallback to the former private `_async_array` attribute. The path is used for basic asynchronous reads as well as orthogonal and vectorized indexing.

**Why this matters to practitioners:** xarray/Zarr pipelines should not depend indefinitely on a private attribute that Zarr may change or remove. The fallback preserves compatibility with older versions during the transition, reducing the risk of a future break between the two libraries.

**Possible action:** monitor. Add at least one Zarr version before 3.1.4 and one recent version to the compatibility matrix, covering asynchronous reads and `oindex`/`vindex`; wait for an xarray release before production.
