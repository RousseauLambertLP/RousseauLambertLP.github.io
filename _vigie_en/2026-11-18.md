Four changes clear the publication threshold. MCP Servers 2.5.0 is a published security release. GPT-6.2 Astra and Sol were announced after the previous watch and are included as a dated catch-up. The GDAL and Zarr changes are merged into their main branches but are not yet included in a stable release.

## 1. MCP Servers 2.5.0 fixes eight vulnerabilities in three servers

**Date:** November 18, 2026  
**Status:** published release  
**Practical importance:** high for agents accessing Git repositories, filesystems, or URLs

Release 2.5.0 fixes six paths in `mcp-server-git`, a confinement flaw in `server-filesystem`, and a NAT64 bypass in `server-everything`. The Git scenarios include programs configured by a repository running during automatic maintenance, lazy object fetching, filter or merge drivers, and submodule processing. A crafted Git index could also expose the contents of a file outside the working tree. The filesystem server now anchors listings to the checked directory on Linux and macOS; that protection remains incomplete on Windows.

**Why this matters to practitioners:** an agent handling code, business rules, or data files often treats repositories and directories as untrusted input. A nominally read-only mode is insufficient if a Git command can indirectly start a program defined by the repository.

**Possible action:** update. Install `mcp-server-git` 2026.11.18, `@modelcontextprotocol/server-filesystem` 2.4.0, and `@modelcontextprotocol/server-everything` 2.3.1 when these components are used. Old date-versioned npm releases do not migrate automatically to 2.4.0 because their version number sorts higher, so an explicit installation is required. Continue isolating untrusted repositories and account for the documented Windows limitations.

**Primary source:**

- MCP Servers v2.5.0 release: <https://github.com/modelcontextprotocol/servers/releases/tag/v2.5.0>

## 2. OpenAI releases GPT-6.2 Astra and GPT-6.2 Sol

**Date:** November 17, 2026  
**Status:** models and API published  
**Practical importance:** high for agents, tool calling, and turning knowledge into workflows

OpenAI presents Astra as its frontier model for complex work and Sol as its general-purpose model aimed in part at agents. Both accept text and images, provide a 1.05-million-token context window, and allow up to 128,000 output tokens. At announced Standard pricing, Astra costs US$8 per million input tokens and US$40 for output; Sol keeps GPT-6.1 Sol pricing at US$2 and US$10. Published benchmark results are vendor evaluations, not independent validation on weather or geospatial tasks.

Migration is not only a model-name change: tool calling requires the Responses API, reasoning effort `none` is rejected, several sampling and log-probability parameters must be removed, and prompt caching now adds cache-write billing with specific retention options.

**Why this matters to practitioners:** the large context window and tool calling can help connect OGC documentation, schemas, rules, and geospatial APIs in an agent. API, caching, and cost changes still need evaluation before migration, and weather-text generation should remain grounded in authorized facts with deterministic validation.

**Possible action:** test. Using public or synthetic data, compare Astra and Sol on rule extraction, structured output, API calls, and fact validation. Measure total cost, including caching, and verify incompatible parameters. Do not transfer work data without appropriate authorization.

**Primary sources:**

- OpenAI announcement: <https://openai.com/index/introducing-gpt-6-2-astra-sol/>
- GPT-6.2 migration guide: <https://developers.openai.com/api/docs/guides/latest-model>
- Official model directory: <https://developers.openai.com/api/docs/models>

## 3. GDAL fixes OpenFileGDB spatial filtering in Web Mercator with recent PROJ

**Date:** November 17, 2026  
**Status:** fix merged into `master`; absent from GDAL 3.13.3  
**Practical importance:** high for bbox-filtered Web Mercator FileGDB layers

With PROJ 9.7.1 or later, a change in how the base CRS axis order was interpreted could lead OpenFileGDB to compute zero Y bounds for its spatial index. A valid bbox filter then returned no features when a spatial index was used. The fix enforces the expected axis order while computing the index.

**Why this matters to practitioners:** an empty result could be interpreted as a real absence of data rather than a filtering error. FileGDB datasets created by GDAL with PROJ 9.7.1 or later may already contain an invalid `.spx` file whose northings are all zero; upgrading the code does not repair that existing index.

**Possible action:** test and correct locally when needed. Compare results with and without the spatial index on a Web Mercator layer, then rebuild indexes produced with affected versions. Wait for a GDAL release containing the fix before considering distributed environments corrected.

**Primary sources:**

- GDAL pull request #15510: <https://github.com/OSGeo/gdal/pull/15510>
- Merged commit: <https://github.com/OSGeo/gdal/commit/e64eee09b258c11a98ad913f20c7f465b853d888>
- Original report #15337: <https://github.com/OSGeo/gdal/issues/15337>

## 4. Zarr narrows partial reads of uncompressed chunks to the requested region

**Date:** November 18, 2026  
**Status:** feature merged into `main`; absent from Zarr-Python 3.4.2  
**Practical importance:** medium to high for cloud-native access to small windows

Zarr-Python extends partial decoding when a selection touches only one index on the first axis and narrow slices on following axes. A read such as `arr[t, y0:y1, x0:x1]` can now fetch only the required rows of an uncompressed chunk instead of the complete frame; a point selection may read only one item.

**Why this matters to practitioners:** weather and geospatial APIs frequently extract a point or small window from a spatiotemporal cube. On an object store or through HTTP Range, reading fewer bytes can reduce latency and transfer costs. The gain still depends on encoding, chunk shape, and backend; it does not apply indiscriminately to every codec.

**Possible action:** test. Measure requests, bytes transferred, and latency for point/tile extraction on a representative store, then compare with Zarr-Python 3.4.2. Wait for a published release before changing production.

**Primary sources:**

- Zarr-Python pull request #4611: <https://github.com/zarr-developers/zarr-python/pull/4611>
- Merged commit: <https://github.com/zarr-developers/zarr-python/commit/6eb45631d909cbf915c70d70a90e9d2726ad46fa>
