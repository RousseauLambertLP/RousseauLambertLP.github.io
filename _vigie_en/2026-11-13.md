Seven recent changes clear today’s publication threshold. All are merged into development branches, but none is included in an announced stable release yet.

## 1. MapServer fixes a type confusion causing a `heap-buffer-overflow`

**Date:** November 12, 2026  
**Status:** fix merged into `main`; no CVE or release announced  
**Practical importance:** high for services accepting external OGC filters

A `PropertyIsEqualTo` literal whose value was `PropertyIsLike` could be interpreted and freed as an `FEPropertyIsLike` node, causing a heap buffer overflow. OSS-Fuzz found the defect. The fix now checks the node type as well as its textual value.

**Why this matters to you:** WMS/WFS and other interfaces accepting Filter Encoding expressions can process client-controlled documents. A malformed input must not be able to terminate the MapServer process.

**Possible action:** track the backport to the 8.6 branch and the next corrective release. Add the OSS-Fuzz case to untrusted-input tests; do not describe current stable versions as fixed.

**Primary sources:**

- MapServer pull request #7679: <https://github.com/MapServer/MapServer/pull/7679>
- Merged commit: <https://github.com/MapServer/MapServer/commit/884a4f19681a6bb157496685d41b0944e8833c32>
- Proposed 8.6 backport: <https://github.com/MapServer/MapServer/pull/7688>

## 2. GDAL closes an information leak despite `ALLOW_FILE_ACCESS=NO`

**Date:** November 12, 2026  
**Status:** fix merged into `master`; not yet released  
**Practical importance:** high for APIs validating client-supplied CRS definitions

`SetFromUserInput()` could still call `stat()` on a path when `ALLOW_FILE_ACCESS=NO` was active. Error codes differed depending on whether the file existed, allowing filesystem probing. The fix no longer touches the path and now returns a uniform result.

**Why this matters to you:** CRS validation is a common input boundary in geospatial APIs. Disabling file reads should also prevent disclosure of file presence.

**Possible action:** add tests comparing existing and nonexistent paths, then adopt a release containing the fix. This recent change was not selected for the previous edition.

**Primary sources:**

- GDAL issue #15479: <https://github.com/OSGeo/gdal/issues/15479>
- Merged pull request #15499: <https://github.com/OSGeo/gdal/pull/15499>
- Merged commit: <https://github.com/OSGeo/gdal/commit/696d7438467908f8468739ce24af83c2fc91a25f>

## 3. GDAL fixes multidimensional HDF5 attribute values

**Date:** November 12, 2026  
**Status:** fix merged into `master`; not yet released  
**Practical importance:** high for multidimensional HDF5/NetCDF metadata

The multidimensional API advanced the source pointer by one element at each dimension instead of using the dimension stride. A 2 × 3 attribute containing `0…5` could therefore be read as `0,1,2,1,2,3`. Classic `gdalinfo` was unaffected, but `gdalmdiminfo` and the multidimensional API returned incorrect values.

**Why this matters to you:** scientific attributes can control units, axes, quality, or interpretation of a weather cube. A silently incorrect read is more dangerous than an explicit failure.

**Possible action:** test non-trivial 2D and 3D attributes in HDF5/NetCDF validation and compare the classic API, multidimensional API, and h5py.

**Primary sources:**

- GDAL pull request #15509: <https://github.com/OSGeo/gdal/pull/15509>
- Merged commit: <https://github.com/OSGeo/gdal/commit/2e13e4b82ac38020ed7dc7a98a4c4ced7226c415>

## 4. xarray shares read-only HDF5 file handles

**Date:** November 12, 2026  
**Status:** change merged; not yet released  
**Practical importance:** medium to high for processing that opens several groups or variables from one file

xarray now reuses one HDF5 handle for identical local read-only opens with `h5netcdf` or `netCDF4`, until the last dataset closes. Write modes and NetCDF3 retain their behavior. The change also covers locks, pickling, and distributed workers.

**Why this matters to you:** weather workflows opening several groups from the same NetCDF4 file could multiply handles, thrash the file cache, and expose fragile HDF5 interactions.

**Possible action:** test with real multi-group access patterns, distributed Dask, and explicit closing. Measure handles and memory before and after; wait for a release before deployment.

**Primary sources:**

- xarray pull request #11809: <https://github.com/pydata/xarray/pull/11809>
- Merged commit: <https://github.com/pydata/xarray/commit/819c63708617f47cc271229a45a753dbe43c0451>

## 5. GDAL adds `gdal crs info`

**Date:** November 12, 2026  
**Status:** feature merged into `master`; not yet released  
**Practical importance:** medium for automated CRS inspection and validation

The new command ports `gdalsrsinfo` capabilities into the unified CLI: validation, EPSG identification, and WKT, PROJJSON, PROJ.4, MapInfo, or XML output. It also supports structured `--json-usage` help.

**Why this matters to you:** it simplifies reproducible CRS diagnostics in pipelines and can provide tools or agents with a more consistent interface than the separate legacy executable.

**Possible action:** prepare parity tests with `gdalsrsinfo`, especially for `--validate`, `--identify`, and PROJJSON. Do not change production scripts before a release includes the command.

**Primary sources:**

- GDAL pull request #15441: <https://github.com/OSGeo/gdal/pull/15441>
- Merged commit: <https://github.com/OSGeo/gdal/commit/a077f4a553b53bb2d1364259d3018201d11f882a>

## 6. MapServer stabilizes rendering of nearly collinear joins

**Date:** November 13, 2026  
**Status:** fix merged into `main`; not yet released  
**Practical importance:** medium for dynamic cartography

For some outer joins between nearly parallel segments, the AGG calculation could place the intersection point millions of pixels away. MapServer now falls back to the plain offset point when the intersection exceeds `width × miter_limit`.

**Why this matters to you:** a valid but numerically unfavorable geometry could produce pathological rendering, an oversized image, or disproportionate processing cost in a weather map service.

**Possible action:** retain a regression case with nearly collinear lines and track the 8.6 backport before upgrading.

**Primary sources:**

- MapServer pull request #7683: <https://github.com/MapServer/MapServer/pull/7683>
- Merged commit: <https://github.com/MapServer/MapServer/commit/499756acc8f644592b7017ea1975cb8e10ffe3d9>
- Proposed 8.6 backport: <https://github.com/MapServer/MapServer/pull/7690>

## 7. `zarr-metadata` makes codec definitions stricter

**Date:** November 12, 2026  
**Status:** breaking change merged; 0.8.0 changelog prepared, but no release confirmed  
**Practical importance:** medium for Zarr V3 metadata validators and generators

V3 codecs are now represented by distinct classes for array→array, array→bytes, or bytes→bytes transitions, instead of `CodecDefinition(kind=...)`. Data types also declare a `number_class`, used to reject invalid combinations earlier, such as `scale_offset` with a string.

**Why this matters to you:** tools turning format rules into machine-actionable validation can detect impossible codec/dtype pipelines before accessing chunks. The Python API changes incompatibly, however.

**Possible action:** pin the dependency and test the codecs actually used by weather cubes. Prepare migrations away from `CodecDefinition(kind=...)`, then wait for the 0.8.0 release.

**Primary sources:**
