## 1. PHP: two critical vulnerabilities now have fixes

**Published: October 21, 2026 · Status: security releases published · Practical importance: critical where PHP is present in exposed infrastructure.**

Yesterday’s advance notice is now a complete advisory. The PHP project confirms that **CVE-2026-109618** and **CVE-2026-109619** can allow unauthenticated remote code execution. The fixed releases are:

- PHP **8.5.12**
- PHP **8.4.27**
- PHP **8.3.36**
- PHP **8.2.35**

The project states that no mitigation is a complete solution: updating is the only safe choice. PHP 8.1 and older branches no longer receive regular upstream releases. Distribution and long-term-support vendors may provide backported fixes; the project also published minimal source backports for PHP 7.4, 8.0 and 8.1 to help environments that still need to build those versions.

**Primary source:** [PHP — official archive and October 21, 2026 advisory](https://www.php.net/archive/2026.php).

### Why it matters

The vulnerability is not announced in MapServer, GDAL or pygeoapi. It is nevertheless relevant to a geospatial platform if PHP is installed in an image, used by an adjacent Web application or required by a PHP MapScript deployment.

The priority is therefore to verify actual exposure rather than assume that the entire geospatial stack is affected.

### Recommended action

1. Inventory PHP on hosts, inside containers and in deployment images, for example with `php -v` and the appropriate package manager.
2. Upgrade to a fixed release or apply the patch supplied by the distribution/LTS vendor.
3. Rebuild and redeploy affected images; updating the host does not automatically fix a runtime embedded in a container.
4. If immediate updating is impossible, consult the temporary measures in the official advisory, while treating them as exposure reductions rather than complete fixes.

No action is required for services whose inventory confirms that PHP is absent.
