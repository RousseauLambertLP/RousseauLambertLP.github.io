Three code changes merged since the previous edition clear the publication threshold. They are not released versions yet: they should be tracked or tested from development branches without assuming they are present in stable packages.

## 1. Zarr-Python reads extension shorthand names allowed by Zarr V3.1

**Date:** November 8, 2026  
**Status:** fix merged into the zarr-python main branch; no new release published  
**Practical importance:** high for Zarr V3.1 data-cube interoperability

Zarr V3.1 allows some configuration-free extensions to be represented by a simple name, such as `"crc32c"`, instead of the object `{"name": "crc32c"}`. Zarr-Python could nevertheless reject this valid metadata with a type error. The fix now expands these shorthand forms for codecs, including nested sharding, the chunk grid, chunk-key encoding, and storage transformers. Extensions that require configuration are still rejected when that configuration is missing.

To retain compatibility with V3.0 readers, Zarr-Python continues to write the object form rather than the shorthand form.

**Why this matters to you:** a weather cube produced by another Zarr V3.1-compliant writer can be valid yet unreadable with a current zarr-python release. This is a concrete interoperability case for cloud-native pipelines and xarray/Dask processing.

**Possible action:** add compatibility fixtures containing shorthand codecs, nested sharding, and shorthand `chunk_key_encoding`; track the next zarr-python release before relying on the fix in production.

**Primary sources:**

- zarr-python pull request #4506: <https://github.com/zarr-developers/zarr-python/pull/4506>
- Merged commit: <https://github.com/zarr-developers/zarr-python/commit/e6658d22c282d96641af1e3779bfb47c66d9ead7>

## 2. `zarr-metadata` adds a preflight check for whether a V3 node is actually openable

**Date:** November 8, 2026  
**Status:** feature merged into the `zarr-metadata` subproject; no release published  
**Practical importance:** medium to high for automated pipelines, catalogues, and agents

The new `read_openable_node_metadata_v3` reader reports declarations a reader cannot interpret: an unknown codec, data type, or chunk grid, as well as an unknown top-level member that is not explicitly marked `"must_understand": false`. General-purpose readers remain permissive to preserve format extensibility.

**Why this matters to you:** this check distinguishes valid JSON metadata from a dataset that a given environment can actually open. A catalogue, ETL pipeline, or agent can therefore detect an incompatibility before starting an expensive Dask computation or incorrectly claiming that a resource is usable.

**Possible action:** prototype this reader as a prevalidation step and retain unrecognized declarations in a structured diagnostic; do not treat it as available in a stable version until it is released.

**Primary sources:**

- zarr-python pull request #4604: <https://github.com/zarr-developers/zarr-python/pull/4604>
- Merged commit: <https://github.com/zarr-developers/zarr-python/commit/f50cce1300cc76203757c503cc9af92e6d1f2203>

## 3. GDAL correctly initializes the ordinal of an SQLite FID field also exposed as an attribute

**Date:** November 8, 2026  
**Status:** fix merged into the GDAL main branch; no new release published  
**Practical importance:** medium, but limited to affected OGR/SQLite schemas

In `OGRSQLiteTableLayer::RecomputeOrdinals()`, the ordinal of an FID column that was also created as a regular field was not initialized before the counter was incremented. The defect was found with MemorySanitizer. The fix initializes the ordinal and adds a test that checks the FID, the regular FID field, and neighbouring attributes together.

**Why this matters to you:** this narrow case can affect column-to-attribute mapping when reading SQLite tables that expose their identifier as a normal field. Services or conversions built on OGR need that mapping to be reliable.

**Possible action:** add a regression test that opens an SQLite layer whose FID is also an attribute and compare the FID, that field, and adjacent columns; wait for a GDAL release before assuming the fix is present in distributions.

**Primary sources:**

- GDAL issue/patch #15490: <https://github.com/OSGeo/gdal/issues/15490>
- Merged commit: <https://github.com/OSGeo/gdal/commit/15c79ff06cbc32a6631bdf303b956aa7210c7ad3>
