Five changes deserve practical attention. The November 3 GeoDjango advisory is included today because its two CRS/GDAL vectors directly affect geospatial-service security and had not been retained in previous editions. The other four changes were merged on November 6 but are not yet releases. No sufficiently significant new development was confirmed for GeoMet, WIS2, MapServer, PROJ/pyproj, OGC, OKF, or weather AI.

## 1. GeoDjango fixes two CRS-related SSRF and local-file-read vectors

**Date:** November 3, 2026  
**Status:** Django 6.1.3, 6.0.10 and 5.2.19 security releases published  
**Practical importance:** high for any API accepting untrusted geometries or CRS definitions

Two advisories directly concern the geospatial stack. CVE-2026-111362 fixes acceptance of external CRS references in GeoJSON geometries that GDAL could resolve through network or file access. CVE-2026-114582 affects strings passed to `SpatialReference`, `transform()` methods, and several `srs`/`srid` setters, which could likewise issue outbound requests or read local files.

Django rates the first advisory moderate and the second low. Full `SpatialReference` protection requires GDAL 3.9 or newer; with an older GDAL version, Django recommends integer SRIDs or an allow-list for strings. The new `gis.W001` system check warns when GDAL is too old.

**Why it matters to you:** a weather or geospatial API may receive geometries, CRS definitions, or reprojection parameters. Even when GeoMet does not use GeoDjango, these advisories illustrate the risk of allowing a geospatial library to resolve client-supplied URLs or paths implicitly.

**Possible action:** inventory Django GIS services, update to a patched version, verify that GDAL is at least 3.9, and run system checks. For any other API, prefer allow-listed CRS identifiers over arbitrary definitions obtained from the network.

**Primary sources:**

- Django security announcement: <https://www.djangoproject.com/weblog/2026/nov/03/security-releases/>
- Django 6.1.3 release notes: <https://docs.djangoproject.com/en/6.1/releases/6.1.3/>

## 2. pygeoapi fixes a race in OGC API — Processes callbacks

**Date:** November 6, 2026  
**Status:** change merged into `master`, not yet published in a release  
**Practical importance:** high for deployments using process subscribers

The process manager kept the current processor in shared mutable state, so concurrent executions could overwrite one another. The fix now keeps the processor in a local variable and passes its `allow_internal_requests` setting explicitly to `inProgressUri`, `successUri`, and `failedUri` notifications. A disallowed subscriber URL now produces a dedicated HTTP 400 error.

**Why it matters to you:** asynchronous-job callbacks sit on a sensitive SSRF boundary. The decision to allow or deny an internal address must belong to the process actually being executed, without depending on mutable state shared across requests.

**Possible action:** add a concurrent test with two processes that have different internal-access policies, including callbacks to loopback and private ranges. Wait for a pygeoapi release containing the commit before treating distributed installations as fixed.

**Sources:**

- pygeoapi pull request #2479: <https://github.com/geopython/pygeoapi/pull/2479>
- Merged commit: <https://github.com/geopython/pygeoapi/commit/133f077e11ffdd966c2f0117b7adcb1dca30f132>

## 3. GDAL fixes a use-after-free in `Geometry.AddGeometryDirectly()`

**Date:** November 6, 2026  
**Status:** fix merged into `master`, not yet published in a GDAL release  
**Practical importance:** medium to high for Python OGR code handling geometry ownership

The Python bindings did not preserve the ownership relationship correctly when a child geometry was transferred with `AddGeometryDirectly()`. After the parent or feature was destroyed, the child’s Python wrapper could still refer to freed memory. The fix now records the parent and transferred reference, with lifetime tests.

**Why it matters to you:** geospatial ETL code that assembles rings, polygons, or compound geometries in Python can crash or behave unpredictably depending on object collection order. This is not presented as a CVE or as a remotely exploitable vulnerability.

**Possible action:** add a test that explicitly destroys the parent after `AddGeometryDirectly()` and then checks the child’s behaviour. Wait for a GDAL release containing the fix; in the meantime, avoid reusing an object whose ownership was transferred.

**Sources:**

- GDAL pull request #15466: <https://github.com/OSGeo/gdal/pull/15466>
- Merged commit: <https://github.com/OSGeo/gdal/commit/a9678354d99f44466a93dbc68fcd80b78a7fc355>

## 4. MCP documents and fixes a `oneOf` validation pitfall in tool schemas

**Date:** November 6, 2026  
**Status:** examples and documentation merged into current revision 2026-07-28 and draft; not a new normative release  
**Practical importance:** medium for agent tools with structured inputs

The `find_resource` example placed property definitions and types inside `oneOf` branches. A request containing both properties could therefore make one branch inapplicable by giving one property the wrong type and still be accepted by the other branch. The fix moves `properties` to the schema root and reserves `oneOf` for presence assertions using `required`. The documentation now calls out this JSON Schema authoring pitfall.

**Why it matters to you:** agent tools that invoke weather or geospatial APIs must validate identifiers, extents, and options before execution. A schema that appears strict can accept an incorrectly typed combination when type constraints are trapped inside composition branches.

**Possible action:** test MCP schemas using `oneOf`, `anyOf`, or `allOf` with simultaneous and deliberately mistyped properties. Keep common types at the root and use branches for conditional constraints.

**Sources:**

- MCP pull request #3185: <https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3185>
- Merged commit: <https://github.com/modelcontextprotocol/modelcontextprotocol/commit/38353251fab3bdeead03dd8283b9e66076ce1a7f>

## 5. Zarr-Python fixes orthogonal indexing with an array followed by `...`

**Date:** November 6, 2026  
**Status:** fix merged into `main`, not yet published  
**Practical importance:** medium for multidimensional-cube selections

A selection such as `z.oindex[[1, 2], ...]` failed because Zarr compared `Ellipsis` with a NumPy array using `==`, producing a Boolean array with an ambiguous truth value. The fix now compares the ellipsis by identity and covers integer index arrays and Boolean masks, for both reads and writes.

**Why it matters to you:** this is a natural syntax for selecting a subset of stations, levels, or forecast steps while preserving the remaining dimensions of a weather cube. The error can occur independently of the data values.

**Possible action:** add `oindex` tests using lists, NumPy arrays, Boolean masks, and an ellipsis for reads and writes. Wait for a Zarr-Python release containing the commit before a production upgrade.

**Sources:**

- Zarr-Python pull request #4595: <https://github.com/zarr-developers/zarr-python/pull/4595>
- Merged commit: <https://github.com/zarr-developers/zarr-python/commit/659531808ee2e98435dc6e3a33f846970b5f269d>
