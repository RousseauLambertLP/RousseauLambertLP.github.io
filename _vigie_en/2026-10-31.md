## 1. GDAL: possible crash during highly concurrent multithreaded warps on Windows

**Reported: October 30, 2026 · Status: open issue and unmerged proposed fix · Practical importance: medium and conditional.**

A report targeting **GDAL 3.13.3** describes process terminations on Windows 10 under a workload combining 12 Python processes with many `gdal.Warp(..., multithread=True)` calls using `NUM_THREADS=8`. The report's analysis locates a race in `CPLCreateJoinableThread()`: a very short-lived thread can finish before the creating thread records its handle, potentially leading to a double free when the thread is joined.

The associated pull request changes synchronization during Windows thread creation. At the time of this edition, it is **open, unmerged and absent from any published release**. The report and proposed fix target the Windows implementation; they do not show that the pthread path used on Linux is affected. This is a precise upstream report, not independent validation across every warp scenario.

**Why it matters:** raster reprojection or clipping pipelines may combine process-level parallelism with GDAL's own threading. The risk is most relevant to Windows development workstations or batch processing that enables `multithread=True` under high concurrency; the sources do not justify a general change for Linux services.

**Action: test and monitor.** Inventory Windows jobs that combine several processes with multithreaded warps, then add a representative stress test. If this crash pattern is observed, reducing concurrency or temporarily disabling multithreaded warp is an operational mitigation to validate, not an official fix. Monitor the pull request and wait for a merge followed by a published GDAL release before treating the issue as fixed upstream.

**Primary sources:** [OSGeo/GDAL — issue #15452](https://github.com/OSGeo/gdal/issues/15452) · [OSGeo/GDAL — pull request #15451](https://github.com/OSGeo/gdal/pull/15451).
