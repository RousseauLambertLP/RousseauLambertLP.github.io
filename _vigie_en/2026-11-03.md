## 1. Zarr-Python fixes `longlong` recognition on Linux and macOS

**Merged: November 2, 2026 at 09:48 EST · Status: fix merged into `main`, not yet released · Practical importance: medium to high for NumPy/Zarr pipelines.**

Zarr-Python did not correctly recognize the NumPy `longlong` and `ulonglong` aliases on Linux and macOS. These types are signed and unsigned 64-bit integers, but NumPy assigns them dtype classes distinct from `Int64DType` and `UInt64DType`. Zarr validation could therefore reject arrays that were equivalent to `int64` or `uint64`.

The fix now compares the integer kind and dtype size rather than only its Python class. It also generalizes checks that were already needed for some integer aliases on Windows.

**Why it matters:** weather or geospatial pipelines can produce identifiers, counters or time coordinates using platform-dependent NumPy aliases. Before the fix, the same array could be accepted on one system and rejected on another before it was written to a Zarr store.

**Action: test and monitor.** Add a Linux/macOS Zarr round-trip for `np.longlong` and `np.ulonglong`, covering Zarr formats 2 and 3 if both are used. Wait for a published Zarr-Python version containing the fix before treating the problem as resolved in stable environments.

**Primary source:** [zarr-developers/zarr-python — pull request #4589](https://github.com/zarr-developers/zarr-python/pull/4589).

## 2. GDAL preserves backslashes in PostgreSQL string lists

**Merged: November 2, 2026 at 11:00 EST · Status: fix merged into `master`, not yet released · Practical importance: medium and conditional for OGR/PostgreSQL.**

OGR’s PostgreSQL driver stripped backslashes while reading an `OFTStringList` field. In the documented case, `c:\data` was returned as `c:data`. The fix changes deserialization and adds a create, write and read-back test for lists containing paths and escaped quotes.

**Why it matters:** this defect can silently alter technical metadata, paths, expressions or other escaped strings stored in a PostgreSQL array and exposed through OGR. It does not affect ordinary text fields or every PostgreSQL read.

**Action: test if `OFTStringList` is used.** Add a round-trip test with backslashes and quotes, then monitor the next GDAL release. No general migration is warranted when the relevant schemas do not use PostgreSQL string lists.

**Primary source:** [OSGeo/GDAL — pull request #15430](https://github.com/OSGeo/gdal/pull/15430).

## 3. xarray now honors `drop=True` with custom indexes that retain scalar coordinates

**Merged: November 3, 2026 at 08:40 EST · Status: fix merged into `main`, not yet released · Practical importance: medium for raster sampling and custom indexes.**

With a custom index that rebuilds a selected position as a scalar coordinate, `isel(..., drop=True)` or `sel(..., drop=True)` could retain that coordinate despite the documented contract. xarray now removes the corresponding scalar coordinates. If a selection attempts to drop only some coordinates owned by the same index, the call now raises an error to avoid corrupting the index.

xarray’s built-in indexes do not follow this path and their behavior is unchanged.

**Why it matters:** custom indexes such as a `RasterIndex` can represent the spatial axes of a data cube together. A pixel or point extraction using `drop=True` may therefore produce different coordinates — or raise on a partial selection — after a future upgrade.

**Action: test before upgrading.** Cover complete and partial scalar selections with the custom indexes actually in use, then check the resulting coordinates and `xindexes`. No immediate action is required for objects that use only xarray’s built-in indexes.

**Primary source:** [pydata/xarray — pull request #11617](https://github.com/pydata/xarray/pull/11617).
