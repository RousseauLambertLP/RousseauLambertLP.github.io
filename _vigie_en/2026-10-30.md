## 1. Official MCP servers: eight vulnerabilities fixed across three packages

**Published: October 25, 2026 · Status: security release published · Practical importance: high for any agent using these servers.**

Version **2.1.0** of the official `modelcontextprotocol/servers` repository fixes eight vulnerabilities in `@modelcontextprotocol/server-filesystem`, `@modelcontextprotocol/server-everything` and `mcp-server-fetch`. The fixes cover, among other issues, escapes from allowed directories through symlink swaps or case differences, cross-origin access to the Everything server, and SSRF bypasses in Fetch involving IDNA names, NAT64 and `robots.txt` redirects.

The fixed versions are `@modelcontextprotocol/server-filesystem@2.0.1`, `@modelcontextprotocol/server-everything@2.0.1` and `mcp-server-fetch@2026.10.24`. One trap matters: older date-versioned npm packages in the `2025.x` or `2026.x` ranges sort above `2.0.1`, so an automatic upgrade may not offer the fix.

**Why it matters:** an agent that can access files, URLs, documentation or geospatial APIs places these servers directly on the trust boundary. A flaw can turn an untrusted catalogue, Web page or local path into out-of-scope access.

**Action: update.** Inventory deployed versions, explicitly install the fixed versions where date-versioned packages are present, then retest directory listings, writes and URL retrieval. On Windows, read the filesystem server advisory: the symlink-race fix is only partial there.

**Primary source:** [modelcontextprotocol/servers — version 2.1.0](https://github.com/modelcontextprotocol/servers/releases/tag/v2.1.0).

## 2. Zarr-Python 3.4.2 hardens reads and fixes several production cases

**Published: October 27, 2026 · Status: version 3.4.2 published · Practical importance: medium to high for Zarr/xarray/Dask pipelines.**

Zarr-Python 3.4.2 now requires explicit opt-in before reading data encoded with the `pickle` codec. The release also bounds memory used while cleaning up chunks after a resize, resets the codec-pipeline thread pool after `fork`, and fixes lazy opening and non-truncating reopening of `ZipStore`. It also corrects the default scalar value for `bytes` fields in structured data types.

**Why it matters:** the `pickle` opt-in reduces implicit execution of untrusted content, but can break a workflow that silently depended on this codec. The memory, `fork` and `ZipStore` fixes directly affect parallel processing, workers and Zarr archives.

**Action: test before updating.** Run read/write tests with xarray and Dask, including structured types, resizes, multiprocessing workers and `ZipStore`. Check historical datasets that use `pickle` separately; enable it only for trusted data.

**Primary source:** [zarr-developers/zarr-python — version 3.4.2](https://github.com/zarr-developers/zarr-python/releases/tag/v3.4.2).

## 3. GPT-6.1 Terra targets visual reasoning and computer use at lower cost

**Published: October 26, 2026 · Status: model and API available · Practical importance: medium for automating mapping interfaces.**

OpenAI released `gpt-6.1-terra` in the API and in ChatGPT Work and Codex. The model accepts text and images and supports structured outputs, tool calling, MCP and computer use, with a 1.05-million-token context window. Announced standard API pricing is **US$1/M input tokens**, **US$0.05/M cached input tokens** and **US$5/M output tokens**, half the standard price of GPT-6.1 Sol.

The speed and quality gains reported by OpenAI come from its own evaluations; they are not independent validation on weather or geospatial tasks.

**Why it matters:** a lower-cost, vision-oriented model can be useful for testing map-interface reading, visual layer checks or automation of a Web procedure. It does not replace numerical data validation or deterministic checks on units, projections, forecast times and weather thresholds.

**Action: test in a bounded setting.** Compare Terra with a reference model on a small set of public or synthetic tasks: selecting layers, reading legends, capturing states and producing verifiable structured outputs. Use an isolated browser, limit actions, and do not transfer work data without appropriate authorization.

**Primary sources:** [OpenAI — GPT-6.1 Terra model card](https://developers.openai.com/api/docs/models/gpt-6.1-terra) · [OpenAI — model announcement](https://openai.com/index/introducing-gpt-6-1-terra/).

## 4. OKF: new proposals on provenance, routing and addressing — not yet adopted

**Opened: October 25–26, 2026 · Status: open community proposals, not merged into the specification · Practical importance: monitor.**

The canonical `GoogleCloudPlatform/open-knowledge-format` repository received several proposals: adding `digest` and `revision` to sources, a `sections` registry for addressing part of a document, a BCP 47 language field, `priority` and `scope` hints, and mechanisms for transferability or persistent agent-author identities. The current specification remains **OKF v0.2**; these issues are neither a new release nor an adopted standard.

**Why it matters:** these proposals target the needs of an agent-usable weather/geospatial knowledge base: source traceability, bilingual selection, addressing a business rule, and controlling knowledge transfer between domains. Their number also shows that interoperability has not yet stabilized.

**Action: monitor, with no immediate migration.** Continue producing conformant v0.2 and pin the specification revision in use. For a prototype, keep these ideas in clearly documented extension fields; do not present them as standardized OKF fields until a change to `SPEC.md` is merged and versioned.

**Primary sources:** [canonical OKF v0.2 specification](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md) · [open proposals in the OKF repository](https://github.com/GoogleCloudPlatform/open-knowledge-format/issues).
